## 实验目的

本实验解释`洋葱`如何真正运作：每一跳、每个方向都有独立的加密密钥与运行摘要；客户端按照经过的跳数，为消息包裹多层加密。中间中继不能预先判断收到的值是否发给自己，还是需要继续去掉一层的中转消息。它先尝试识别；如果识别失败，就转发解密处理后的结果。

最重要的是，我们将真正的电路一次扩展一跳，直到抵达出口。

## 核心实现

洋葱本身的关键只有两个循环：

```python
def encrypt(self, msg: RelayMessage, destination: int | None = None) -> bytes:
    d = len(self.hops) - 1 if destination is None else destination
    body = self.hops[d].forward.sign(encode_relay(msg))
    for i in range(d, -1, -1):
        body = self.hops[i].forward.apply(body)
    return body

def decrypt(self, body: bytes) -> tuple[int, RelayMessage]:
    for i, hop in enumerate(self.hops):
        body = hop.backward.apply(body)
        if hop.backward.recognizes(body):
            return i, decode_relay(body)
    raise CellError("没有任何跳点能够识别该 cell：应关闭电路")
```

`recognizes` 比看起来复杂。它要求 `Recognized` 字段为零，**而且**运行摘要匹配。如果摘要验证失败，真实摘要状态必须保持不变，否则一次误判就会永久破坏电路同步。因此实现先在副本（`self.digest.copy()`）上检查，仅在成功时才采用副本状态。

这些是 `ClientCircuitCrypto` 和 `Circuit` 方法的节选；依赖的导入、类型和状态在完整 Python 模块中定义。

## 常见问题

| 现象 | 原因 |
|---|---|
| `没有任何跳点能够识别该 cell：应关闭电路` | 摘要状态失去同步，常见原因是在识别失败时仍更新了运行摘要 |

# 实现详解

相关模块有两个：`labs/zh-Hans/代码/torlab/encryption.py`（约 115 行，负责洋葱加密机制），以及 `labs/zh-Hans/代码/torlab/circuit.py`（约 115 行，组合通道、CircID 与多跳）。

## `Direction` 保存什么？

```python
POS_DIGEST = slice(5, 9)
POS_RECOGNIZED = slice(1, 3)

def _aes_ctr(key):
    return Cipher(algorithms.AES(key), modes.CTR(bytes(16))).encryptor()

def _without_digest(body):
    return body[:5] + bytes(4) + body[9:]
```

**IV 是零值**，并不是简化。Tor 中的 CTR 状态在一条电路的生命周期内跨 cell 持续推进，因此每条新 cell 都使用新的密钥流部分。如果为每条 cell 重新初始化密码器，就会重复使用密钥流，严重破坏加密安全性，即使程序表面上还能工作。

```python
@dataclass
class Direction:
    cipher: object
    digest: "hashlib._Hash"
```

`Direction` 将必须同步推进的两类状态组合在一起：AES-CTR 密码器状态与运行摘要。它们在规范中是不同概念，但实现时相互关联。每跳有正向、反向两个方向，因此三跳电路维护六个 `Direction` 对象。

## 加密与解密使用同一种原语

```python
def apply(self, data):
    return self.cipher.update(data)
```

在 CTR 模式下，加密与解密都是把数据和密钥流 XOR。这种对称性解释了为什么中间中继能使用相同原语`去掉一层`。

同时，AES-CTR 具有**可篡改性**：密文翻转一个比特，就会使明文对应比特翻转。运行摘要用于检测这类修改；本书附录 B 明确演示了这一性质。

## 摘要不是针对单条 cell 的

```python
def sign(self, body):
    self.digest.update(_without_digest(body))
    return body[:5] + self.digest.digest()[:4] + body[9:]
```

运行摘要**只累计在此方向上发往本跳或由本跳产生的 relay 消息**，不包括转发给其他跳点的消息。`update` 会累积状态，所以每条已接受消息都依赖前面的历史。

规定顺序为：使用 `_without_digest` 清空 Digest 字段，将这种表示加入运行哈希，取结果的前四字节并写入 Digest。接收方执行相同计算。

因此，**丢失或重新排序 relay cell 会永久破坏运行状态同步**。Tor 不尝试从这种情况恢复，而是关闭电路。

普通电路的运行摘要使用 SHA-1，洋葱服务电路则使用 SHA3-256。这里的 SHA-1 用途由特定协议构造决定，不能简单等同于普通的抗碰撞安全场景。

## 识别过程及保护电路状态的副本

```python
def recognizes(self, body):
    if body[POS_RECOGNIZED] != b"\x00\x00":
        return False
    candidate = self.digest.copy()
    candidate.update(_without_digest(body))
    if candidate.digest()[:4] != body[POS_DIGEST]:
        return False                 # 误判时不更新状态
    self.digest = candidate
    return True
```

这是整个模块最容易出错的步骤。

第一道过滤条件是 Recognized：如果不为零，就说明当前中继不是消息目标，不得更新摘要状态。

但两字节随机值碰巧全零的概率约为 $1/65536$。此时必须用摘要进行第二道检查。如果在发现 Digest 不匹配之前就更新真正的运行摘要，一次假阳性就会破坏之后所有消息的验证。

先 `copy()`，只在成功时提交状态，让失败的识别过程**没有副作用**，从而保持电路同步。

## 两个洋葱循环

```python
def encrypt(self, msg: RelayMessage, destination: int | None = None) -> bytes:
    d = len(self.hops) - 1 if destination is None else destination
    body = self.hops[d].forward.sign(encode_relay(msg))
    for i in range(d, -1, -1):
        body = self.hops[i].forward.apply(body)
    return body

def decrypt(self, body: bytes) -> tuple[int, RelayMessage]:
    for i, hop in enumerate(self.hops):
        body = hop.backward.apply(body)
        if hop.backward.recognizes(body):
            return i, decode_relay(body)
    raise CellError("没有任何跳点能够识别该 cell：应关闭电路")
```

出站流量先使用目标跳点的运行摘要签名，然后从最内层目标向外逐层加密。入站流量从外向内逐层去除加密，每去掉一层就尝试识别。

注意，`decrypt` 事先不知道消息来自哪一跳。它通过逐层去除加密并检查识别字段来确定来源，这与 Tor 中继处理 relay 消息的方式相对应。

## 扩展电路

```python
def extend(self, r: RelayInfo, extensions=()) -> list[tuple[int, bytes]]:
    st, hd = ntor3_client_start(r.id_ed, r.ntor, encode_extensions(list(extensions)))
    body = extend2_body("127.0.0.1", r.port, r.id_rsa, r.id_ed, HTYPE_NTOR_V3, hd)
    self.send(RelayMessage(RelayCommand.EXTEND2, 0, body), early=True)
    hop, msg = self.receive()
    if msg.command != RelayCommand.EXTENDED2:
        raise CircuitError(f"电路扩展失败：{RelayCommand(msg.command).name}")
    sm, k = ntor3_client_finish(st, hdata_created2(msg.data))
    self.crypto.hops.append(Hop.from_keys(CircuitKeys.from_stream(k)))
    return decode_extensions(sm)
```

实现错误时最容易导致难以解释故障的三个细节：

- **StreamID 零值：**`EXTEND2` 控制电路而不是应用程序流。
- **使用 `RELAY_EARLY`，不是 `RELAY`：**扩展请求必须使用限制次数的特殊 cell（[实验 17](实验-17-relay-early.md)）。
- **中继身份：**本例在 `EXTEND2` 中同时提供 RSA 与 Ed25519 链路标识。规范并不要求每个 `EXTEND2` 都必须带 Ed25519；如果执行扩展的中继通过共识知道该身份，则应对其进行检查。缺少 Ed25519 字段本身不必然导致 `DESTROY`。

本示例中的拥塞控制**只在最后一跳**请求：`(1, b"")` 扩展发往出口，而非中间中继。

## 关于内存测试的局限

`test_encryption.py` 能有效检查不变量，但模拟两端使用相同源码。两端都使用同一实现时，可能漏掉对称性缺陷。因此，与正式 `tor` 的独立互操作仍是必要的验证。

## 实践注意事项

- 电路密钥来自 ntor 密钥流：20+20 字节摘要材料（`Df`、`Db`），以及 16+16 字节加密密钥（`Kf`、`Kb`），合计 72 字节，顺序不能弄错。
- 每个方向的**初始摘要状态**由 `Df` 或 `Db` 提供种子，而不是从空哈希开始。
- `Direction` 包含持续推进的 CTR 状态，所以不能跨电路复用。
- 如果预期属于自己的消息出现 `没有任何跳点能够识别该 cell：应关闭电路`，应检查所有可能在不该推进时推进了运行摘要的分支。
