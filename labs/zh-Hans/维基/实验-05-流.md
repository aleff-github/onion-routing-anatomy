## 实验目的

教学客户端能够通过三个中继下载完整的 1 MB 文件，并得到与原始文件相同的 SHA-256 摘要。第二项试验故意做正常客户端不应做的事：**停止发送 `SENDME`**，统计出口在暂停前发送了多少条 `DATA` cell。这个数字直接揭示当前窗口大小，也使旧式流量控制与新版拥塞控制的差别可见。

## 准备

本实验仅用于实验 1–4 的**私有 Tor/Chutney 网络**。如实验网络尚未运行，请先启动 `labs/zh-Hans/实验室` 环境；教学客户端不适用于公共 Tor 网络。Web 服务器需要位于客户端与实验中继可访问的本地主机 loopback 环境。

在端口 8080 启动本地 Web 服务器，提供一个 1 MiB 文件：

```bash
cd /tmp/labweb && python3 -m http.server 8080 --bind 127.0.0.1 &
```

回到仓库后设置：

```bash

```

## 运行实验

```bash
python3 - <<'EOF'
import hashlib
import time
from pathlib import Path
from torlab.circuit import build
from torlab.laboratory import relay
from torlab.stream import Stream

circ = build([relay("003r"), relay("004r"), relay("006e")])
s = Stream(circ, 1)
t = time.time()
s.open("127.0.0.1", 8080)
s.send(b"GET / HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
r1 = s.receive_all()
print(f"流 1： {len(r1)} 字节，耗时 {time.time()-t:.2f} s, DATA cell {s.reg.data_cells}, "
      f"电路 SENDME 累计 {circ.sendme_sent}, 其他消息 {s.reg.others}")

s = Stream(circ, 2)  # 第二条流，共用同一电路
t = time.time()
s.open("127.0.0.1", 8080)
s.send(b"GET /grande.bin HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
r2 = s.receive_all()
print(f"流 2： {len(r2)} 字节，耗时 {time.time()-t:.2f} s, DATA cell {s.reg.data_cells}, "
      f"电路 SENDME 累计 {circ.sendme_sent}, 其他消息 {s.reg.others}")

headers, sep, payload = r2.partition(b"\r\n\r\n")
if not sep or b" 200 " not in headers.split(b"\r\n", 1)[0]:
    raise RuntimeError("HTTP response is missing or is not 200 OK")
reference = Path("/tmp/labweb/grande.bin").read_bytes()
assert len(reference) == len(payload) == 1048576, "HTTP file length differs"
expected_sha = hashlib.sha256(reference).hexdigest()
received_sha = hashlib.sha256(payload).hexdigest()
assert received_sha == expected_sha, "download SHA-256 does not match local file"
print("接收文件的 SHA-256：", received_sha)
print("SHA-256 与本地文件一致")
EOF
```

## 参考输出

以下记录说明输出的形式。随机文件内容、HTTP 响应头、目录列表及 DATA cell 数量都可能变化。脚本运行时会检查 HTTP 200 响应、有效文件长度及 SHA-256 是否与本地原文件相同。

```text
流 1：... DATA cell 1，... 电路 SENDME 累计 0，...
流 2：... DATA cell 2120，... 电路 SENDME 累计 68，...
接收文件的 SHA-256：<本次随机文件的64位十六进制摘要>
SHA-256 与本地文件一致
```

成功的 `BEGIN` 会收到 `CONNECTED`。IPv4 响应体可以是 8 字节地址与 TTL，但规范也允许空响应体或 IPv6 格式。`7f000001 00000708` 只是历史示例，不是固定的地址或 TTL。电路级 SENDME 只统计**由目标出口针对该电路的流产生的 DATA cell**，不把中间中继单纯转发的其他数据计算进去。在示例中 1 + 2120 条 DATA cell、每 31 条确认一次，得到 floor(2121 / 31) = 68 个电路级 SENDME。这不是普适常数。1048781 个 HTTP 字节至少需要 ceil(1048781 / 498) = 2106 条 cell，2120 只体现部分 cell 未填满。

## 使本实验具有教学价值的错误

最初实现将电路 `SENDME` 计数器放在**流**对象中。只需要少量 cell 的第一条流能够工作；随后传输 1 MB 的第二条流却收到 `DESTROY`，电路被关闭。

原因是，电路 `SENDME` 必须累计**该电路上所有流**的 `DATA`。出口已经计入了流 1 的数据，因此在流 2 中更早期待下一次 `SENDME`。客户端发送得太迟，并附带了与出口预期不同的运行摘要。第 289 号提案要求收到此类错误时关闭电路。将计数器移入 `Circuit` 后问题得到解决。

电路 `SENDME` 是**经过认证**的：它携带触发确认的 cell 对应的运行摘要。没有真正接收和处理流量的一方，不能轻易伪造确认，让发送方毫无限制地继续传输。

## 直接观察窗口

```bash
python3 - <<'EOF'
from torlab.circuit import build
from torlab.laboratory import relay
from torlab.stream import Stream
for cc in (True, False):
    circ = build([relay("003r"), relay("004r"), relay("006e")], cc=cc)
    circ.count_received_data = lambda: None       # 不发送电路级 SENDME
    s = Stream(circ, 1)
    s.open("127.0.0.1", 8080)
    s.send(b"GET /grande.bin HTTP/1.0\r\n\r\n")
    circ.channel.sock.settimeout(6)
    try:
        s.receive_all()
    except TimeoutError:
        pass
    print(f"拥塞控制={cc}：出口暂停前收到 {s.reg.data_cells} 条 DATA cell")
EOF
```

下列数字基于此私有实验网络的一种配置：拥塞控制初始窗口为 124 条 cell（4 × `sendme_inc=31`），旧式流窗口为 500。共识参数、Tor 版本与网络条件都可能改变结果。**124 不等于恰好四条 TLS 记录**；这里只表示四组 31 条 DATA cell。**500** 说明旧式流窗口可能先于默认 1000 条电路窗口耗尽。出口在窗口耗尽后暂停产生新的 DATA cell，并不意味着所有未发送的数据都已经存在于其应用缓存中。

```text
拥塞控制=True：出口暂停前收到 124 条 DATA cell
拥塞控制=False：出口暂停前收到 500 条 DATA cell
```

教学代码的 `Stream` 类**未实现流级 SENDME**。在成功协商拥塞控制（`cc=True`）时可以不使用流级确认；在 `cc=False` 时，大文件会在 500 条 DATA cell 的流窗口处停住，即使电路级 SENDME 正常发送也是如此。这是用于观察历史窗口的**刻意限制**，不能将该简化实现视为完整的旧式客户端。

# 实现详解

相关代码是约 80 行的 `labs/zh-Hans/代码/torlab/stream.py`，加上 `circuit.py` 中电路级 `SENDME` 的部分。到这里，教学客户端从协议演示进入真正的文件传输。

## 打开一条流

```python
def begin_body(address: str, port: int, flag: int = 0) -> bytes:
    """小写且以 NUL 结尾的 ADDRPORT；FLAGS 为零时省略。"""
    body = f"{address.lower()}:{port}".encode() + b"\x00"
    return body + (struct.pack(">I", flag) if flag else b"")

```

该编码函数包含三个细节，必须区分规范性要求与建议：

- **小写（SHOULD）：**Tor 建议将 `ADDRPORT` 以小写发送，以降低客户端指纹风险；接收方**必须**接受大小写混合的字符串。小写并非强制拒绝条件。
- **NUL 结尾：**字段采用 C 风格零终止字符串，不使用独立的长度前缀。
- **FLAGS 为零时省略：**只有请求额外地址族行为（如 IPv6）时才需要可选 FLAGS 字段。

```python
def open(self, address: str, port: int) -> bytes:
    self.circ.send(RelayMessage(RelayCommand.BEGIN, self.id, begin_body(address, port)))
    _, msg = self._next()
    if msg.command == RelayCommand.END:
        raise CircuitError(f"BEGIN 请求被拒绝：{END_REASONS.get(msg.data[0], msg.data[0])}")
    if msg.command != RelayCommand.CONNECTED:
        raise CircuitError(f"收到意外的 BEGIN 回应：{msg.command}")
    return msg.data
```

教学客户端与正式 tor 有一项刻意保留的差异，它与客户端指纹识别有关。规范要求 `EXTEND2` 使用 `RELAY_EARLY`，还建议把剩余配额用于最初约八条发自起点、并非发给第一跳的 relay 消息。tor 遵循这一建议：在 `src/core/or/relay.c` 中，只要 `remaining_relay_early_cells>0` 且 `cpath_layer != origin_circ->cpath`，就会使用 `RELAY_EARLY`。因此，tor 通常使用 `RELAY_EARLY` 发送初始 `BEGIN`；教学客户端除了 `EXTEND2`，则一律使用普通 `RELAY`。

这种差异确实有影响：计数 early cell 的入口守卫可能把教学客户端与正式 tor 区分开。我们保留简单实现，以便每次实验集中介绍一个概念；书中完整会话示意图展示了真实生产行为。

出口以 `CONNECTED`（包含解析地址与 TTL）或带原因码的 `END` 回应。原因码有实际运维意义：`EXITPOLICY` 表示当前出口拒绝目标，改用其他出口可能成功；`CONNECTREFUSED` 则表示选中的出口到达了目的地址，但远端拒绝连接。[实验 14](实验-14-出口策略.md)会直接检验出口策略行为。

协议还允许客户端在收到 `CONNECTED` 之前发送应用数据，以节省一次电路往返。为了讲解清晰，本教学客户端先等待 `CONNECTED`。

## 流量控制与关键错误

```python
def count_received_data(self) -> None:
    """每收到最终跳点的一条 DATA cell 就调用一次；
    每累计 `sendme_inc` 条就发送一次经过认证的 SENDME（版本 1）。"""
    est = dict(self.exit_extensions)
    sendme_inc = est[2][0] if 2 in est else 100
    self.data_to_ack += 1
    if self.data_to_ack == sendme_inc:
        self.data_to_ack = 0
        # 摘要来自触发 SENDME 的已识别 cell 处理完成之后的运行状态：
        # 参见 src/core/crypto/relay_crypto_tor1.c 的 sendme_digest。
        digest = self.crypto.hops[-1].backward.digest.digest()
        body = struct.pack(">BH", 1, 20) + digest
        self.send(RelayMessage(RelayCommand.SENDME, 0, body))
        self.sendme_sent += 1
```

**此方法属于 `Circuit`，不是 `Stream`。** 原始缺陷把计数器分别放在各条流中。当前一条流已经消耗部分电路配额时，后续流的摘要确认时机就会出错。

其他重要细节包括：

- **`sendme_inc`** 来自[实验 3](实验-03-握手.md)与出口协商得到的扩展 2。启用拥塞控制时为 31；本实验的传统流量控制为 100。它是协商状态，不应硬编码成客户端固定属性。
- **摘要**来自触发 `SENDME` 的 `DATA` cell **处理完成之后**，最后一跳反向运行摘要的当前值。只有真正处理过相关流量的一方，才知道这个内部电路状态。
- **版本 1、长度 20** 表示以 SHA-1 为基础、经过认证的电路 `SENDME`。版本 0 不含摘要，容易被伪造确认；第 289 号提案引入认证机制。
- **StreamID 零值**表示电路控制消息。流本身另有独立窗口及流级确认机制。

> 经过认证的 `SENDME` 不是数字签名，更接近一种**接收证明**：知道所需的运行摘要，表明接收方处理过相应 cell。

## 接收循环

```python
def receive_all(self) -> bytes:
    """读取 DATA 直至 END，必要时发送电路级 SENDME。"""
    parts = []
    while not self.closed:
        _, msg = self._next()
        if msg.command == RelayCommand.DATA:
            parts.append(msg.data)
            self.reg.received_data += len(msg.data)
            self.reg.data_cells += 1
            self.circ.count_received_data()
        elif msg.command == RelayCommand.END:
            self.closed = True
            self.reg.others.append(f"END {END_REASONS.get(msg.data[0] if msg.data else 1)}")
        else:
            self.reg.others.append(RelayCommand(msg.command).name)
    return b"".join(parts)
```

计数和确认发生在**接收循环内部**。如果客户端停止读取，也就停止确认，发送方最终会耗尽窗口。流量控制自然地依赖接收数据的行为。

`self.reg` 汇总字节、`DATA` cell 及其他消息的统计，方便实验说明为何真实传输通常需要超过 `ceil(bytes/498)` 下限的 cell：出口会随数据到达立即发送，不必等待填满一整条 relay cell。

## 测量窗口大小

```python
circ = build(path, cc=cc)
circ.count_received_data = lambda: None      # 不发送 SENDME
```

用空操作取代原方法，只用于实验。它直接回答一个容易停留在抽象层面的问题：**出口在流量控制阻止它之前，究竟会发送多少个 cell？**

观察到的答案分别为 124（启用拥塞控制）和 500（未启用），取决于哪个有效窗口先耗尽。预计是 1000 条历史电路窗口的读者可能会感到意外：本实验中先到限制的是流窗口。

## 实践注意事项

- 必须有监听**端口 8080** 的服务器。它也是完整实验验证的使用端口，运行测试前先停止手工服务器。
- 测试文件必须足够大，能超过当前窗口。如果数据不足约 124 条 cell（60 KB 左右），拥塞控制实验就很难观察出效果。
- 同一电路上的 StreamID 必须**互不相同且不为零**。
- 如果大文件传输以 `DESTROY` 结束，首先检查电路 SENDME 计数是否由所有流共享，而不是分别计算。
