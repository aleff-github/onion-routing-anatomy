## 实验目的

**514 字节**仅适用于链路协议版本 4 及以上的定长 cell；版本 3 使用 2 字节 CircID 和 512 字节 cell。

Tor cell 是一种结构简单但严格的二进制格式：4 字节 CircID、1 字节命令以及 509 字节消息体，**总计 514 字节**，与承载的内容无关。统一长度避免从 cell 总长度直接推断消息类型。变长 cell（`VERSIONS` 和编号不小于 128 的命令）是例外。`VERSIONS` 总使用两字节 CircID，因为它在链路协议版本协商之前发送。

## 运行实验

```bash
python3 - <<'EOF'
from torlab.cells import *

# 1. 定长 cell
c = Cell(0x80000001, CellCommand.RELAY, b"\x01" * 509)
g = encode(c, 4)
print("length:", len(g), "| first 8 bytes:", g[:8].hex())

# 2. 解码：返回 cell 和尚未消耗的字节
decoded_cell, remaining = decode(g, 4)
print("decoded:", hex(decoded_cell.circ_id), CellCommand(decoded_cell.command).name, "| remaining:", len(remaining))

# 3. 变长 cell
print("VERSIONS:", encode(Cell(0, CellCommand.VERSIONS, b"\x00\x04\x00\x05"), 4).hex())

# 4. 位于 cell 消息体内的 relay 消息
m = RelayMessage(RelayCommand.BEGIN, 1, b"127.0.0.1:80\x00")
r = encode_relay(m)
print("relay message:", len(r), "byte | header:", r[:11].hex())
rit = decode_relay(r)
print("decoded:", RelayCommand(rit.command).name, rit.stream_id, rit.data)
EOF
```

## 参考输出

```text
length: 514 | first 8 bytes: 8000000103010101
decoded: 0x80000001 RELAY | remaining: 0
VERSIONS: 000007000400040005
relay message: 509 byte | header: 010000000100000000000d
decoded: BEGIN 1 b'127.0.0.1:80\x00'
```

如何解读：

- `8000000103` 由 CircID `0x80000001`（最高位为 1，表示本通道的发起方建立该电路）和命令 `3`（`RELAY`）组成。
- `VERSIONS` 是 `0000`（**两字节** CircID）+`07`（命令）+`0004`（长度）+`0004 0005`（提供协议版本 4 和 5）。
- relay 消息头依次是 `01`（`BEGIN`）、`0000`（Recognized）、`0001`（StreamID）、`00000000`（Digest 暂时为空，实验 4 会填入摘要）及 `000d`（13 字节数据）。

`Cell.command` 和 `RelayMessage.command` 都是整数。借助 `CellCommand(...)` 和 `RelayCommand(...)` 可以打印可读的符号名称。

# 实现详解

全部实现位于约 220 行的 `labs/zh-Hans/代码/torlab/cells.py` 中。后续每个实验都依赖它。这里的一处错误可能直到几章以后才表现为中继悄然关闭电路。

以下函数示例摘自完整的 `cells.py`，所需导入和辅助定义位于原始模块的其他位置。

## 常量

```python
CELL_BODY_LEN = 509          # 定长 cell 的消息体字节数
RELAY_HEADER_LEN = 11        # relay 消息头长度
RELAY_DATA_MAX = CELL_BODY_LEN - RELAY_HEADER_LEN   # 498
```

`RELAY_DATA_MAX` 并不是直接从规范抄来的数字，而是其他两个长度的**结果**。用减法表达，而非硬编码 `498`，能够清楚表示格式之间的关系。格式也可能改变：CGO relay 加密（第 359 号提案，tor 源码已经支持）使用另一种头部格式，而第 340 号提案甚至准备将消息和 cell 分离。

命令采用 `IntEnum` 而非普通 `Enum`。二进制协议需要把命令作为整数比较与编码，必须能够执行 `bytes([cell.command])`，同时仍希望保留可读的名称。

```python
def circid_len(version):
    return 2 if version < 4 else 4

def is_variable_length(command):
    return command == CellCommand.VERSIONS or command >= 128
```

CircID 长度由协商出的链路协议版本决定：版本 3 及之前是两字节，从版本 4 开始是四字节。将规则集中到辅助函数，避免在模块各处散布魔法数字。

`>= 128` 来自协议规范：命令字节的最高位表示变长 cell。`VERSIONS`（命令 7）是历史例外，因为它早于该约定。

## `encode`

```python
def encode(cell: Cell, version: int) -> bytes:
    """按照链路协议 `version` 序列化 cell。

    VERSIONS 始终按版本 0 编码（两字节 CircID），
    因为发送时双方尚未协商链路协议版本。
    """
    if cell.command == CellCommand.VERSIONS:
        version = 0
    n = circid_len(version)
    if not 0 <= cell.circ_id < 1 << (8 * n):
        raise CellError(f"CircID {cell.circ_id:#x} 无法容纳在 {n} 字节中")
    header = cell.circ_id.to_bytes(n, "big") + bytes([cell.command])
    if is_variable_length(cell.command):
        if len(cell.body) > 0xFFFF:
            raise CellError("变长 cell 的消息体过长")
        return header + struct.pack(">H", len(cell.body)) + cell.body
    if len(cell.body) > CELL_BODY_LEN:
        raise CellError(f"消息体长度 {len(cell.body)} 字节超过 {CELL_BODY_LEN}")
    # 使用零值填充至 CELL_BODY_LEN（tor-spec，body-padding）。
    return header + cell.body.ljust(CELL_BODY_LEN, b"\x00")
```

最初两行是容易令人困惑的特殊情况：`VERSIONS` 在链路版本确认**之前**传输，因此其格式不能依赖尚未协商的版本。强制 `version=0` 便使 CircID 长度为两字节。它是唯一必须在协商结果之外单独确定格式的 cell，否则版本协商根本无法开始。

`"big"` 表示网络字节序，Tor 的整数采用这种顺序。显式检查 CircID 范围在技术上并非必要，因为 `to_bytes` 本来也会抛出 `OverflowError`，但自定义错误能说明哪个值超界、可用字节有多少，更适合教学。

两类 cell 在这里分开处理：

- **变长：**先写入两字节 `Length`，再逐字节写入消息体。长度已经明确，不需要固定长度填充。
- **定长：**将消息体用零填充到**509 字节**。规范要求如此，接收方忽略这些填充字节。

> 定长 cell 的填充属于链路层数据：直接连接的 TLS 对端解密后可读，外部窃听者不可见。relay 消息填充受洋葱加密保护，只有识别并解密消息的目标跳点可读取。

## `decode`

**接收 `VERSIONS` 时必须使用版本 0：**协商前应调用 `decode(buffer, 0)`，按照两字节 CircID 读取。协商后再使用 `decode(buffer, negotiated_version)` 处理其他 cell；提前传入 4 会错误解析头部。

```python
def decode(buffer: bytes, version: int) -> tuple[Cell, bytes] | None:
    """从 `buffer` 中提取第一条完整 cell。

    返回 (cell, remaining_bytes)；若缓冲区数据尚不完整则返回 None，
    因为 TLS 数据可能按任意大小的分片到达。
    """
    n = circid_len(version)
    if len(buffer) < n + 1:
        return None
    circ_id = int.from_bytes(buffer[:n], "big")
    command = buffer[n]
    if is_variable_length(command):
        if len(buffer) < n + 3:
            return None
        (length,) = struct.unpack(">H", buffer[n + 1:n + 3])
        end = n + 3 + length
        body_start = n + 3
    else:
        end = n + 1 + CELL_BODY_LEN
        body_start = n + 1
    if len(buffer) < end:
        return None
    return Cell(circ_id, command, buffer[body_start:end]), buffer[end:]
```

此函数设计为每次从 socket 收到字节就调用，即使当前可能还没有一条完整 cell。因此它有**三次独立的完整性检查**，恰好对应简单解析器处理真实网络流量时最容易出错的位置：

1. 没有完整的 CircID 与命令，就不知道采用哪种 cell 格式。
2. 对变长 cell，还需再读取两字节长度字段。
3. 最后，必须等到整个消息体到齐。

返回 `None` 表示`更多字节到达后再调用`，而不是协议错误。调用代码因而保持简单：

```python
while True:
    result = decode(buffer, version)
    if result is None:
        chunk = sock.recv(4096)
        if not chunk:
            raise EOFError("connection closed before a complete cell")
        buffer += chunk
        continue
    cell, buffer = result
    ...
```

TLS 记录和 cell 边界并不相同，一次读取可以包含片段或多条 cell。16 KiB 理论上可容纳 31 条 514 字节的完整 cell，但不意味着每条 TLS 记录总是如此。

教学客户端使用不可变的 `bytes`，每次调用都切出剩余数据。生产实现通常使用环形缓冲区等高效结构，避免反复复制尾部。对于中继级吞吐量，这种区别很重要。

## `negotiate_version`

```python
def negotiate_version(ours: list[int], received_body: bytes) -> int:
    """选择双方共同支持的最高版本（tor-spec，VERSIONS-cells）。"""
    if len(received_body) % 2:
        raise CellError("VERSIONS 消息体字节数不能为奇数")
    theirs = {v for (v,) in struct.iter_unpack(">H", received_body)}
    common = set(ours) & theirs
    if not common:
        raise CellError("双方没有共同支持的链路协议版本")
    return max(common)
```

奇数字节数不可能构成完整的两字节整数列表，因此必须直接拒绝，不能猜测。接着计算双方版本集合的交集，并根据规范选择**最高**的共同版本。

自然会有人问：中间人如果从列表中删除更新的版本，导致**降级**，怎样阻止？这个辅助函数本身无法发现。保护来自周围的通道协议：

- 协商已经在 TLS 内部进行，[实验 1](实验-01-通道.md)还会通过 `CERTS` 将通道绑定到中继身份。
- 如果发起连接的一方也是中继并执行身份认证，`AUTHENTICATE` 摘要覆盖交换过的**全部**字节，包括 `VERSIONS`，因此篡改会被发现。

## `encode_relay`

```python
def encode_relay(msg: RelayMessage, random_bytes=os.urandom) -> bytes:
    """生成 RELAY cell 的 509 字节明文消息体。

    填充方式：四个零字节后接随机字节（tor-spec，relay-cell-padding）。
    摘要另行计算（第 10 章）；本函数直接使用 `msg` 中的摘要值。
    """
    if len(msg.data) > RELAY_DATA_MAX:
        raise CellError(f"每条 cell 最多包含 {RELAY_DATA_MAX} 字节数据")
    header = struct.pack(">BHH4sH", msg.command, msg.recognized,
                               msg.stream_id, msg.digest, len(msg.data))
    space = CELL_BODY_LEN - RELAY_HEADER_LEN - len(msg.data)
    padding = b"\x00" * min(4, space) + random_bytes(max(0, space - 4))
    return header + msg.data + padding
```

一次 `struct.pack` 序列化全部五个头部字段。格式 `">BHH4sH"` 按第 8 章示意图从左到右读取：命令（1 字节）、Recognized（2）、StreamID（2）、Digest（4 字节原始数据，因此写 `4s`）与 Length（2）。总计 11 字节，等于 `RELAY_HEADER_LEN`。

规范以 **SHOULD** 建议：先填最多四个零字节，再填随机字节；若空余不足四字节则全部填零。单靠填充不能判断 relay 消息是否被识别，仍须检查 `Recognized` 和 `Digest`。

| | 定长 cell | relay 消息 |
|---|---|---|
| 填充内容 | 全零 | 最多四个零，余下空间使用随机字节 |
| 谁能明文看到 | 直接连接的 TLS 对端；外部窃听者不可见 | 识别并解密 relay 消息的目标跳点 |
| 目的 | 填满固定长度的消息体 | 使剩余 relay 消息体不可预测 |

如果 relay 消息全部填零，能够猜出真实载荷的攻击者就知道了整个剩余消息体，这会不利于第 289 号提案中的经过认证的 `SENDME` 机制（[实验 5](实验-05-流.md)）。规范以 **SHOULD** 建议：先填最多四个零字节，再填随机字节；若空余不足四字节则全部填零。单靠填充不能判断 relay 消息是否被识别，仍须检查 `Recognized` 和 `Digest`。

`random_bytes` 参数专为测试设计，允许用可预测值替换随机输出。没有这种依赖注入，测试可能只能验证总长度。这是本仓库反复采用的设计原则：**把不确定性的来源作为参数注入，不要将它隐藏在实现内部。**

有关洋葱层中的消息识别与摘要校验，请参见[实验 4](实验-04-加密.md)。
