## 实验目的

密码学握手可以直接根据协议规范实现，并与独立实现互操作；这是最有说服力的验证。实验还展示验证失败时的中继行为：把 MAC 的一个比特翻转，中继返回原因码为 `PROTOCOL` 的 `DESTROY`，而不是容易理解的应用层错误提示。

我们会同时测试四种握手：不带扩展的 ntor-v3、协商拥塞控制的 ntor-v3、经典 ntor，以及 `CREATE_FAST`。

## 运行实验

```bash
python3 - <<'EOF'
from torlab.channel import open_channel
from torlab.cells import Cell, CellCommand, describe
from torlab.laboratory import relay
from torlab.ntor import *

g = relay("003r")
c = open_channel("127.0.0.1", g.port, expected_identity=g.id_ed)

def create(circ, htype, hdata):
    c.send(Cell(circ, CellCommand.CREATE2, create2_body(htype, hdata)))
    r = c.receive()
    print("<-", describe(r, c.version))
    return r

# 1. 不使用扩展的 ntor-v3
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([]))
r = create(0x80000001, HTYPE_NTOR_V3, hd)
sm, _ = ntor3_client_finish(st, hdata_created2(r.body))
print("   ntor-v3 ok, relay message:", decode_extensions(sm))

# 2. 请求拥塞控制的 ntor-v3
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([(1, b"")]))
r = create(0x80000002, HTYPE_NTOR_V3, hd)
sm, _ = ntor3_client_finish(st, hdata_created2(r.body))
print("   ntor-v3 with CC_FIELD_REQUEST ok, response:", decode_extensions(sm))

# 3. 经典 ntor
st, hd = ntor_client_start(g.id_rsa, g.ntor)
ntor_client_finish(st, hdata_created2(create(0x80000003, HTYPE_NTOR, hd).body))
print("   ntor ok")

# 4. CREATE_FAST（仅适用于依赖 TLS 的单跳电路）
x, body = create_fast_client()
c.send(Cell(0x80000004, CellCommand.CREATE_FAST, body))
r = c.receive(); print("<-", describe(r, c.version))
complete_create_fast(x, r.body); print("   CREATE_FAST ok")

# 5. 故意翻转 MAC 的一个比特
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([]))
r = create(0x80000005, HTYPE_NTOR_V3, hd[:-1] + bytes([hd[-1] ^ 1]))
assert r.command == CellCommand.DESTROY and r.body[0] == 1
print("   原因码：", r.body[0], "（MAC 被修改）")

# 6. 未启用拥塞控制却请求 CGO
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([(3, b"\x02\x06")]))
r = create(0x80000006, HTYPE_NTOR_V3, hd)
assert r.command == CellCommand.DESTROY and r.body[0] == 1
print("   原因码：", r.body[0], "（未启用拥塞控制却请求 CGO）")
EOF
```

示例输出保留了部分协议字段及英文调试标签，但原因码说明使用中文；错误文本应以中文版 Python 模块实际抛出的消息为准。

- CC_FIELD_RESPONSE（类型 2）中的 `sendme_inc = 0x1f = 31` 表示启用拥塞控制时**每隔多少个 DATA cell 发送一次 SENDME 确认**。Proposal 324 选用 31 的原因之一是它接近最大 TLS 记录可容纳的定长 cell 数量，但它**不是 TLS 记录容量的规定**。该参数还会出现在[实验 5](实验-05-流.md)和[实验 8](实验-08-洋葱服务.md)涉及的洋葱描述符中。
- **原因码 1 即 `PROTOCOL`。** 这里错误就在当前中继产生，因此能够返回自己的本地原因。转发其他节点生成的 `DESTROY` 时，则不能暴露会泄露故障具体位置的信息。
- 最后一个情况说明扩展间的依赖关系：CGO 必须和拥塞控制一起启用。单独请求 CGO 并不合法。
- 历史私有网络输出中没有观察到 `PADDING` cell，但填充行为取决于协商、链路活动及网络参数；不能据此断言任何单跳电路永远不会出现填充。

## 为什么需要官方测试向量？

两个实现能够通信，尚不能充分证明密码学握手正确：如果双方犯了相同错误，也可能完美互通。`test_ntor.py` 会重现**官方测试向量**：ntor-v3 使用第 332 号提案，ntor HKDF 使用第 216 号提案。输入（包括通常随机生成的密钥）被固定，输出必须逐字节一致。负面测试还要确保修改 `AUTH` 或更换 `VER` 字符串会使握手失败。

对于相同类型和长度的认证值，`hmac.compare_digest` 可以避免在首个不一致字节处直接提前结束；但不能据此保证整个程序的执行时间恒定。

# 实现详解

`labs/zh-Hans/代码/torlab/ntor.py` 约有 240 行。实现时应同时打开协议规范，并用官方测试向量检查。在密码学中，`能运行`不等于`正确`。

以下函数片段摘自当前中文版的完整 `ntor.py` 和 `test_ntor.py`，省略的导入、类型及常量需要从原文件获得。输出来自参考运行。

## 基础原语

```python
NTOR3_PROTOID = b"ntor3-curve25519-sha3_256-1"


def _t(name: str) -> bytes:
    return NTOR3_PROTOID + b":" + name.encode()


def _encap(s: bytes) -> bytes:
    return struct.pack(">Q", len(s)) + s


def _h3(s: bytes, t: bytes) -> bytes:
    return hashlib.sha3_256(_encap(t) + s).digest()


def _mac3(k: bytes, msg: bytes, t: bytes) -> bytes:
    return hashlib.sha3_256(_encap(t) + _encap(k) + msg).digest()


def _kdf3(s: bytes, t: bytes, length: int) -> bytes:
    return hashlib.shake_256(_encap(t) + s).digest(length)
```

这些代码直接实现第 332 号提案附录 A.1 中的公式，并说明三个设计概念。

**域分离。** `PROTOID` 参加每一次计算，防止使用相同原语、甚至相同密钥的其他协议把此处得到的值误当作自己的值。

**用途标签（tweak）。** 同一个哈希构造用不同目的拆分为 `kdf_phase1`、`msg_mac`、`key_seed`、`verify`、`kdf_final` 与 `auth_final`。如果不针对这些用途进行明确域分离，一种用途生成的值就可能与另一种混淆。

**结构化编码。** `_encap` 在每个字节串前添加八字节长度，使拼接结果**没有歧义**。否则，`("ab","c")` 与 `("a","bc")` 都会变成 `"abc"`。密码学编码必须体现结构，而不仅是内容。

需要注意一个细节：在 `_mac3` 中，*密钥*经过封装，消息本身不封装。这正是提案的精确定义。如果觉得`更整齐`而把两者都封装，就会破坏互操作性，测试向量会立即发现。

## 第一阶段：客户端消息

```python
def ntor3_client_start(ID: bytes, B: bytes, message: bytes, ver: bytes = CIRCUIT_VERIFICATION,
                        x: bytes | None = None) -> tuple[Ntor3State, bytes]:
    """ntor-v3 的 CREATE2 HDATA：ID（32）| B（32）| X（32）| 加密消息 | MAC（32）。"""
    sk, X = x25519_generate(x)
    Bx = x25519_dh(sk, B)
    fase1 = _kdf3(Bx + ID + X + B + NTOR3_PROTOID + _encap(ver), _t("kdf_phase1"), 64)
    enc_k1, mac_k1 = fase1[:32], fase1[32:]
    msg_cifrato = aes_ctr(enc_k1, message)          # AES-256-CTR
    mac = _mac3(mac_k1, ID + B + X + msg_cifrato, _t("msg_mac"))
    return Ntor3State(sk, X, B, ID, Bx, mac, ver), ID + B + X + msg_cifrato + mac
```

客户端生成临时密钥对（`sk`、`X`），再计算 Diffie–Hellman 值 **`Bx`**：将自身临时私钥与中继的**静态** `ntor-onion-key` 组合。随后从该值派生两个密钥，分别用于加密与认证客户端握手消息。

> **仅第一阶段，并不为加密的客户端消息提供前向保密。** 因为 `Bx` 依赖中继静态密钥，未来该密钥泄露可能暴露以前记录的第一阶段消息。因此协议在 `CM` 中传输的是协商选项，而非长期应用秘密。电路密钥材料的前向保密来自第二阶段。

可选的 `x` 参数只供测试使用，用于固定通常随机生成的私钥，精确重现提案测试向量。

默认 `ver` 为 `b"circuit extend"`，对应电路扩展。它被纳入密钥派生，因此改变一个字节也会改变派生结果，防止为一种用途生成的握手记录被移用到其他协议场景。

## 第二阶段：中继回应

```python
def ntor3_client_finish(st: Ntor3State, response: bytes,
                      length=CIRCUIT_KEY_MATERIAL_LEN) -> tuple[bytes, bytes]:
    """回应格式为 Y（32）| AUTH（32）| MSG；返回（中继消息，密钥流）。"""
    Y, auth, msg = response[:32], response[32:64], response[64:]
    secret_input = (x25519_dh(st.x, Y) + st.Bx + st.ID + st.B + st.X + Y
                    + NTOR3_PROTOID + _encap(st.ver))
    key_seed = _h3(secret_input, _t("key_seed"))
    verify = _h3(secret_input, _t("verify"))
    auth_input = (verify + st.ID + st.B + Y + st.X + st.mac + _encap(msg)
                  + NTOR3_PROTOID + b"Server")
    if not hmac.compare_digest(_h3(auth_input, _t("auth_final")), auth):
        raise HandshakeError("ntor-v3 AUTH 验证失败")
    stream = _kdf3(key_seed, _t("kdf_final"), 32 + length)
    return aes_ctr(stream[:32], msg), stream[32:]
```

`secret_input` 包含**两个**不同角色的 Diffie–Hellman 值：

| 值 | 计算双方 | 作用 |
|---|---|---|
| `Yx`（`x25519_dh(st.x,Y)`） | 客户端临时密钥 × 中继临时密钥 | **前向保密**：只有长期密钥无法还原 |
| `Bx` | 客户端临时密钥 × 中继静态密钥 | **认证**：只有持有对应静态私钥的中继能派生 |

ntor 的核心就是在一次握手中同时获得两种属性。移除 `Bx` 会失去中继认证；移除 `Yx` 会失去前向保密。

使用 `hmac.compare_digest` 不是表面修饰。它避免按第一个错误字节提前结束，是检查认证值应采用的函数。

最终密钥流并不只包含电路密钥。前 32 字节用于解密中继的握手消息，之后的 72 字节提供 `Df`、`Db`、`Kf` 和 `Kb`，供[实验 4](实验-04-加密.md)进行 relay cell 加密。

## 测试向量是真正的验证

向量测试提供与官方示例逐字节一致的可重复证据，但本身不足以证明所有执行路径的正确性或安全性。

```python
def test_ntor3_vectors_proposal_332():
    st, hdata = ntor3_client_start(h(V["ID"]), h(V["B"]), h(V["CM"]), ver=h(V["VER"]), x=h(V["x"]))
    assert hdata.hex() == V["client"]
    sm, key_stream = ntor3_client_finish(st, h(V["server"]), length=256)
    assert sm == h(V["SM"])
    assert key_stream[:32].hex() == V["keystream_start"]
```

密码学握手必须拿固定输入与逐字节固定输出比较。`test_ntor.py` 复现第 332 号提案的完整 ntor-v3 向量及第 216 号提案的 ntor HKDF 向量。其他测试有意修改 `AUTH` 和 `ver` 并要求失败；否则，一个接受所有结果的验证器也会通过正面向量。

## 四种握手及适用范围

| 握手 | 使用场景 | 说明 |
|---|---|---|
| **ntor-v3** | 当前支持时的默认方式 | 可以在加密消息中协商选项 |
| **ntor** | 不具备新版 relay 协议功能的中继 | 不含协商消息，只建立密钥 |
| **CREATE_FAST** | **仅单跳**电路 | 无额外 DH，依赖底层 TLS |
| TAP | 当前 tor 不再使用 | 已在 tor 0.4.9.1-alpha 中移除 |

`CREATE_FAST` 仅适合第一跳同时也是最后一跳的电路，例如某些目录电路，因为它没有在 TLS 之外提供独立的 Diffie–Hellman 密钥交换。构建普通多跳电路时，不应拿它替代 ntor。

## 实践注意事项

- **中继密钥**由 `torlab.laboratory.relay("003r")` 从实验文件和客户端微描述符读取。尚未下载时，等待网络完成引导。
- **每次测试使用新的 CircID。** 重复使用已经打开的 CircID 会收到 `DESTROY`。
- 通道发起方所建立电路的 CircID 最高位必须为 1（如 `0x80000001`，而非 `0x00000001`），避免与另一端选择的 ID 冲突。
- 握手成功不等于已经建立数据流。收到 `CREATED2` 后，只得到单跳电路与密钥材料；[实验 4](实验-04-加密.md)将继续实现 relay cell 加密与扩展。
