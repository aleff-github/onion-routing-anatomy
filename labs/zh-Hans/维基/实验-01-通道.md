## 实验目的

中继的 TLS 证书**不能单独证明中继身份**。该证书是自签名的，任何人都可以生成。中继通过通道**内部**的 `CERTS` cell 证明其身份：Ed25519 身份与签名密钥绑定，该密钥再与当前 TLS 证书指纹绑定。验证整个证书链，并将认证结果与预期连接的中继身份比较，才能防止中间人冒充我们选择的中继。

## 参考输出

```text
5 785d3199f21d20ad... Netinfo(timestamp=1790265613, peer_address='127.0.0.1', my_addresses=['127.0.0.1']) [3]
   TLS TLSv1.3 TLS_AES_256_GCM_SHA384
   <- VERSIONS（6 字节）
   <- CERTS（1456 字节）
   <- AUTH_CHALLENGE（36 字节）
   <- NETINFO（509 字节）
   -> NETINFO：通道已建立

port 5104 with 003r identity -> 中继身份与预期身份不一致
```

如何解释：

- **`5`** 是协商的链路协议版本。我们与 Arti 一样提供 4 和 5；在这里不再需要版本 3。
- 中继身份的十六进制值**必然可能与示例不同**。每次重新初始化私有网络，都会生成新密钥。`CERTS` 长度也取决于证书内容。
- **`[3]`** 表示该中继允许**其他中继**采用的身份认证方法。我们只是客户端，不向中继认证自己；否则可能生成跨通道可识别的持久身份，反而违背匿名目标。
- 在 `NETINFO` 中，中继提供自己的时间及它观察到的我们所用的地址。客户端回应有意使用**零时间戳、不附带自身地址**，避免泄露时钟和地址信息。
- **历史示例中**，刚建立的通道没有收到 `PADDING`。是否发送填充还取决于电路使用状态、协商及网络参数；只建立一跳连接并不保证观察到填充。[实验 4](实验-04-加密.md)的多跳示例可用于观察相关行为，但不同运行的结果可能变化。

## 最重要的反面测试

实验的最后一行最值得注意：我们实际上连接到 `004r`，却声称预期身份为 `003r`，代码正确拒绝了连接。如果实现只验证证书的签名与有效期，**没有把最终身份与预先选择的身份比较**，它可能通过所有正面测试，却无法防止中继替换攻击。

# 实现详解

`labs/zh-Hans/代码/torlab/channel.py` 约有 260 行代码，负责创建 TLS 连接、验证远端身份，并返回供后续实验发送 cell 的 `Channel` 对象。

以下代码片段摘自 `labs/zh-Hans/代码/torlab/channel.py`。其中部分导入与常量位于完整模块的其他位置，因此单独复制片段并不能作为独立脚本运行。

## 为什么单靠 TLS 不够？

```python
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
```

有安全经验的读者可能认为这三行代码犯了严重错误；但在**这个特定场景**下，它们具有明确的理由。

Tor 中继的 TLS 证书是**自签名**的，没有能够验证的域名，也没有传统证书权威替中继认证。启用 Python 默认的 CA 证书验证，反而会导致所有中继连接失败。身份认证改为在通道**内部**通过 `CERTS` 完成；证书链通过当前 TLS 证书指纹与实际 TLS 会话绑定。

换言之：TLS 提供加密；Tor 协议提供中继身份认证。

> **不要**把上述三行复制到普通 HTTPS 客户端中，否则会关闭其证书保护。它们在这里成立，仅因为后续代码立即验证完整的 Tor 证书链，并与事先选定的中继身份比较。

```python
if os.environ.get("SSLKEYLOGFILE"):
    ctx.keylog_filename = os.environ["SSLKEYLOGFILE"]
```

这遵循浏览器广泛使用的约定：设置 `SSLKEYLOGFILE` 后，TLS 库导出会话秘密，供 Wireshark 解密网络抓包。因此我们才能完成[实验 12](实验-12-流量.md)。这里解密的**只是我们自己的流量**，所需密钥也由自己的程序主动导出。

## 证书链验证

```python
def verify_responder_identity(certificates: dict[int, bytes], cert_tls_der: bytes) -> bytes:
    """遵循规范 Authenticating the responder from its CERTS 中的验证规则。

    如果 Ed25519 身份 -> 签名密钥 -> TLS 证书的认证链合法，
    则返回 32 字节 KP_relayid_ed；否则抛出 ChannelError。
    """
    try:
        id_v_sign = decode_ed_certificate(certificates[CERT_IDENTITY_V_SIGNING])
        sign_v_tls = decode_ed_certificate(certificates[CERT_SIGNING_V_TLS_CERT])
    except KeyError as e:
        raise ChannelError(f"缺少类型 {e.args[0]} 的证书") from None

    identity = id_v_sign.signing_key
    if identity is None:
        raise ChannelError("IDENTITY_V_SIGNING 缺少签名密钥")
    id_v_sign.verify_signature(identity)                      # 由身份密钥自签名
    signing_key = id_v_sign.certified_key             # KP_relaysign_ed
    sign_v_tls.verify_signature(signing_key)
    if sign_v_tls.certified_key != hashlib.sha256(cert_tls_der).digest():
        raise ChannelError("SIGNING_V_TLS_CERT 与实际 TLS 证书不匹配")
    for c in (id_v_sign, sign_v_tls):
        if c.expired():
            raise ChannelError(f"类型 {c.kind} 的证书已过期（expired）")
    return identity
```

该函数包含若干相互独立的身份验证步骤：

| 组件 | 作用 | 防御对象 |
|---|---|---|
| 类型 4 | 将中继身份与签名密钥绑定 | 任意签名密钥冒充中继 |
| `signing_key` | 从扩展 4 读取**谁签署了证书** | 错误地猜测身份，而非读取证书实际声明 |
| 自签名 | 验证类型 4 证书的内部一致性 | 单独作用有限：任何人都能自签名 |
| 类型 5 | 将签名密钥与 TLS 证书绑定 | 当前会话与证书链无关 |
| SHA-256 指纹 | 将所有内容绑定到**这次连接** | 中间人在自己的 TLS 会话中出示诚实中继的证书链 |
| 有效期 | 拒绝已过期证书 | 继续接受已退役的签名密钥 |

最关键的检查是 TLS 证书指纹比较。没有它，证书链即使是真的也没有意义：只能证明声称身份的中继*存在*，不能证明我们*正在与它通信*。

**这里的身份不是普通证书字段：**它是实际签署证书的密钥，记录于扩展 4。证书相当于声明“我是 X，我为密钥 Y 签署证书”；必须从扩展读取 X，不能根据证书来源推断。

## 上述函数之外还缺少的一步

```python
identity = verify_responder_identity(certificates, cert_tls)
if expected_identity is not None and identity != expected_identity:
    raise ChannelError("中继身份与预期身份不一致")
```

一条合法证书链证明连接的是**某台**中继，但不一定是**我们选择的那台**。与预期身份比较，才把一般身份认证变成对目标对象的认证。实验让这一检查故意失败：用 `003r` 的指纹连接 5104 端口。

本实验必须提供 `expected_identity`：API 允许传入 `None`，但那将跳过与预期中继身份的比较，不适用于这里要演示的身份验证。

只检查签名和有效期的实现可能通过正面测试，但无法阻止替换攻击。

## 握手读取循环

```python
while netinfo is None:
    cell, buffer = _read(sock, buffer, version)
    registry.append(f"<- {CellCommand(cell.command).name}（{len(cell.body)} 字节）")
    if cell.command == CellCommand.VERSIONS:
        if version:
            continue                                  # 忽略后续 VERSIONS cell
        version = negotiate_version(SUPPORTED_VERSIONS, cell.body)
    elif cell.command == CellCommand.VPADDING:
        continue
    elif cell.command == CellCommand.CERTS:
        certificates = decode_certs(cell.body)
    elif cell.command == CellCommand.AUTH_CHALLENGE:
        (n,) = struct.unpack(">H", cell.body[32:34])
        methods = [m for (m,) in struct.iter_unpack(">H", cell.body[34:34 + 2 * n])]
    elif cell.command == CellCommand.NETINFO:
        netinfo = decode_netinfo(cell.body)
    else:
        raise ChannelError(f"握手中收到意外的 cell：{cell.command}")
```

- 循环**在收到 `NETINFO` 后结束**，并不假设握手必须恰好包含固定数量的 cell；中间出现的其他合法 cell 可能变化。
- 第二条 `VERSIONS` 必须按规范**忽略**。如果没有 `continue`，后续 `VERSIONS` 可能在握手中途意外再次协商版本。
- 解析 `AUTH_CHALLENGE` 只是为了记录提出的认证方法。我们的角色是客户端，不向中继认证自己的身份，避免产生可跨通道追踪的标识符。
- 最后一个分支非常重要：**凡是没有明确允许的内容，都被视为错误**。`VPADDING` 可以忽略，因为规范允许随时发送。其他意外 cell 则必须拒绝。`else: pass` 看似更宽容，实际上会默默接受任意异常握手序列。

循环结束后还有一个容易忘记的检查：

```python
if certificates is None:
    raise ChannelError("在 CERTS 之前收到了 NETINFO")
```

没有这个判断，恶意节点可能直接发送 `NETINFO` 试图绕过认证，使循环提前结束，并让 `verify_responder_identity` 收到 `None`。

channel.send(client_netinfo_cell(host))

客户端回应中的 `NETINFO` 具有**零时间戳，不提供自己的地址**。这不是为了实验简化；真正的 Tor 客户端也是如此。公布本机时间可能暴露相对稳定的时钟偏差，公布地址则可能泄露客户端不应主动提供的身份信息。

## 实践注意事项

- **重新初始化网络会改变指纹。** `identity_from_file` 读取 `labs/zh-Hans/实验室/net/nodes/<node>/fingerprint-ed25519`。文件格式为 `<name> <base64-key>`，末尾没有 `=` 填充，代码会在解码前补齐。
- **端口规则始终是 `5100 + 节点编号`。**
- 此通道不会发送填充，也不会主动保持连接；闲置几分钟后中继可能主动关闭它（第 7 章）。
- 新通道不会立即收到 `PADDING`。只有通道承载过一条**完整电路**（扩展超过当前中继）或用户流量，中继才启用填充。源码 `channelpadding.c` 对应 `CHANNEL_USED_FOR_FULL_CIRCS` 和 `CHANNEL_USED_FOR_USER_TRAFFIC`。一跳电路不满足条件；[实验 4](实验-04-加密.md)才会看到填充。达到条件后，填充甚至可在首个应用数据之前出现，其行为受到共识参数 `nf_pad_before_usage` 控制，默认值是 1。
