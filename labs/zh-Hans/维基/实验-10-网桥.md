# 实验 10 — 从审查者视角观察 obfs4 网桥

| 项目 | 内容 |

## 实验目标

仅在**自己控制的私有 Chutney 网络**中比较普通 ORPort 的 TLS 与 obfs4 传输。历史抓包显示 TLS 记录以 `16 03 01` 开始，而 obfs4 数据没有被分析器识别为 TLS。**这是特定抓包的观察值，不是绝对不可识别的证明**：已知网桥 IP、连接时序及流量统计仍可被观察或阻断。

普通 TLS 探测无法完成 obfs4 握手。规范要求丢弃无效握手，并**建议**随机延迟之后再关闭连接，但不保证永远静默。

## 准备

**数据安全：**`make ... clean` 会删除生成的 `实验室/net/`，包括私有密钥与日志。仅对可丢弃的本地网络操作，先另存需要保留的数据。若镜像不存在，先运行 `make -C labs/zh-Hans/实验室 image`，因为 `start` 不会自动构建镜像。各语言实验网络共享主机端口，不应同时启动。

本实验使用另外一套网络：网桥权威节点 `003ba`、obfs4 网桥 `009br`，以及网桥客户端 `011bc`。

```bash
make -C labs/zh-Hans/实验室 clean
make -C labs/zh-Hans/实验室 start NETWORK=book-bridge
```

完成实验后，恢复普通网络：

```bash
make -C labs/zh-Hans/实验室 clean
make -C labs/zh-Hans/实验室 start
```

当 `book-bridge` 正在运行时，`make -C labs/zh-Hans/实验室 verify` 检查的就是当前拓扑。网桥客户端的 SOCKS 端口是 **9011**，obfs4 网桥监听 **9909**。

## 步骤一：客户端通过网桥连接

```bash
grep -E "new bridge descriptor|Only one bridge|Bootstrapped 100" labs/zh-Hans/实验室/net/nodes/011bc/notice.log
```

```text
[notice] new bridge descriptor 'test009br' (fresh): $DE539956E7E6A323...~test009br at 127.0.0.1
[warn] Only one bridge (transport: 'obfs4') is configured. You should have at least two
       for conflux, for any transport that is not 'snowflake'.
[notice] Bootstrapped 100% (done): Done
```

日志确认客户端取得已配置网桥的描述符并完成引导，但**单凭这一行不能证明描述符实际通过哪条连接取得**。网桥地址和 obfs4 传输参数必须提前提供给客户端；网桥不在普通公开共识中。Conflux 警告只涉及本配置中的单网桥限制，不表示引导失败。

```bash
docker exec torbook-network curl -s -o /dev/null -w "%{http_code}\n"   --noproxy "" --socks5-hostname 127.0.0.1:9011 http://127.0.0.1:8080/
```

```text
200
```

此检查要求本机端口 8080 已有 HTTP 服务器监听。

## 步骤二：审查者看见了什么？

在另一终端先启动仅对本地开放的 HTTP 服务器：`python3 -m http.server 8080 --bind 127.0.0.1`。以下命令会**覆盖** `b1.pcap`；请先备份重要记录。启动 tcpdump 后分别生成两种流量，并等抓包结束再分析。

在容器内同时捕获网桥 obfs4 端口和普通中继 ORPort 的流量，然后生成两种连接：

```bash
# 仅限自己控制的可丢弃 Chutney 网络
docker exec -u 0 -d torbook-network sh -c \
  "timeout 25 tcpdump -i lo -w /lab/net/b1.pcap 'tcp port 9909 or tcp port 5104' >/dev/null 2>&1"
sleep 2
docker exec torbook-network curl --silent --show-error --max-time 15 \
  --noproxy "" --socks5-hostname 127.0.0.1:9011 http://127.0.0.1:8080/
# 还应打开本地中继的普通 Tor 通道
PYTHONPATH=labs/zh-Hans/代码 python3 - <<'PY'
import ssl
from torlab.channel import ChannelError, open_channel
from torlab.laboratory import relay
r = relay("004r", client="010c")
open_channel("127.0.0.1", r.port, expected_identity=r.id_ed)
PY
sleep 27  # 等 tcpdump 完成
for p in 5104 9909; do
  echo "== 端口 $p =="
  docker exec torbook-network tshark -r /lab/net/b1.pcap \
    -Y "tcp.dstport==$p && tcp.len>0" -T fields -e tcp.len -e tcp.payload | head -1
  docker exec torbook-network tshark -r /lab/net/b1.pcap \
    -Y "tls && tcp.port==$p" -T fields -e frame.number | wc -l
done
```

以下字节和数量来自一次参考抓包，会因运行而异。TLS 的 `16 03 01` 是记录的兼容版本字段，**不能**表示最终协商的 TLS 版本。Wireshark 的 `tls` 分类只是观察性判断，不能证明任何分析器都无法识别 obfs4。它也不隐藏已经为观察者所知的网桥 IP 地址。

```text
== port 5104, first bytes from the client ==
1533   16030105f8010005f4030305cc9ad005e921614509b15f6151135f983b...
== port 9909, first bytes from the client ==
602    f23abb4e8c3a45ab0e92958157c177bba1cc5dd27e80d74db45d77b425...

== packets recognized as TLS ==
port 5104: 29
port 9909: 0

== obfs4 segment sizes (client -> bridge) ==
602 1762 1308 1414 643 2183 2195 1568 1308 2037 616 1346
```

解释抓包：

- **`16 03 01`** 是 TLS 握手记录的开头。普通 ORPort 流量可以被识别为 TLS，同时其目的地址也可能已知属于公开 Tor 中继。
- 发往 obfs4 端口的流量没有相同的 TLS 特征。在记录的抓包中，**没有**数据包被识别为 TLS，TCP 数据段大小也没有与 514 字节的 Tor cell 建立直接对应。
- 精确字节、数据包数量和数据段长度每次都会不同。重要的是可识别 TLS 与混淆传输之间的差别。

## 步骤三：主动探测网桥

怀疑某地址是网桥的审查者可能尝试连接并发送已知协议。在**自己的实验网桥**上使用[实验 1](实验-01-通道.md)的普通 Tor 通道代码向 obfs4 端口连接：

```bash
PYTHONPATH=labs/zh-Hans/代码 python3 - <<'PY'
import ssl
from torlab.channel import ChannelError, open_channel
from torlab.laboratorio import relay
r = relay("004r", client="010c")
try:
    open_channel("127.0.0.1", 9909, expected_identity=r.id_ed)
    raise AssertionError("在 obfs4 端口上意外建立了普通 TLS 通道")
except (TimeoutError, ssl.SSLError, ConnectionResetError, ChannelError) as exc:
    print(type(exc).__name__ + ":", exc)
PY
```

```text
TimeoutError: _ssl.c:1063: The handshake operation timed out
```

普通 TLS ClientHello 并不是有效的 obfs4 握手。历史观察中没有在超时前得到有效响应，其他实现也可能延迟关闭或重置 TCP 连接。`_ssl.c` 的行号取决于 Python/OpenSSL。**一次无响应不等于已证明网桥不可识别**。有效客户端必须事先持有网桥的传输参数和证书材料。

## 自动验证

`make -C labs/zh-Hans/实验室 verify` 只检查**当前运行的 Chutney 拓扑**，并非意大利语 `make verifica-lab-bridge` 的六项专门检查；它不自动生成两种流量抓包，也不执行主动 TLS 探测。

```bash
make -C labs/zh-Hans/实验室 verify
```

这条命令**不会自动切换拓扑**。必须先启动 `book-bridge`，再验证，最后清理它并恢复普通 `book` 网络。

## 常见问题

`make -C labs/zh-Hans/实验室 clean` 只能针对可丢弃网络使用。`pkill -x tor` 会结束**该容器内所有 Tor 进程**，而不只是其中一座网桥。

| 现象 | 原因及建议 |
|---|---|
| 网桥网络始终无法引导 | 上一种拓扑的 tor 进程可能仍占用端口。在确认只是可丢弃的实验网络后，可以使用 `docker exec torbook-network pkill -x tor` 停止它们 |
| `011bc` 未启动 | 客户端属于启动阶段 2，需要 `CHUTNEY_LAUNCH_PHASE=2 chutney start` |
| `tshark` 找不到数据包 | 抓包开始太晚；先运行 `tcpdump`，稍后再产生连接 |
| 节点编号与文档不同 | Chutney 编号来自 `labs/zh-Hans/实验室/chutney/networks/book-bridge` 中的顺序；检查 `labs/zh-Hans/实验室/net/nodes/` |
