## 实验目的

本实验介绍客户端获取中继列表所依赖的目录信任模型，并在私有网络中演示部分密码学检验。权威节点签署共识，微描述符的 SHA-256 摘要记录在对应 `m` 项中。**教学验证器只演示部分关联，并没有独立建立完整信任链。**

同样重要的是，本实验证明验证程序会在**应该失败时失败**：只改动共识中的一个数字，就应导致签名验证失败。

## 运行实验

```bash
python3 - <<'EOF'
import base64
from torlab.circuit import build
from torlab.laboratory import relay
from torlab.directory import *

# 向权威节点建立不使用拥塞控制的单跳目录电路
# 这是 tor 请求目录资料所采用的一种方式
circ = build([relay("000a")], cc=False)
text = download(circ, "/tor/status-vote/current/consensus-microdesc", 1).decode()
c = parse_consensus(text)
print(f"共识：{len(text)} 字节； {' '.join(c.header['valid-after'])}"
      f" -> {' '.join(c.header['fresh-until'])}")

cert = parse_certificates(download(circ, "/tor/keys/all", 3).decode())
print(f"方法 {c.header['consensus-method'][0]}；签名 {len(c.signatures)}；证书 {len(cert)}")
for r in c.relay[:2]:
    print(f"  {r.name} {r.ip}:{r.orport} w={r.bandwidth} flag={sorted(r.flag)[:4]}...")

valid, required, _ = verify_consensus(c, cert, 3)
assert valid >= required, "not enough signatures matching the provided test certificates"
print(f"匹配签名：{valid}（需要：{required}）")

# 负面测试：修改实时共识中任意一个带宽值
# 网络测量值会变动，不要硬编码 Bandwidth=4096 等特定值
import re
bandwidth = re.search(r"Bandwidth=(\d+)", text)
assert bandwidth is not None, "missing Bandwidth field"
altered_text = text.replace(bandwidth.group(0), f"Bandwidth={int(bandwidth.group(1)) + 1}", 1)
assert altered_text != text
modified = parse_consensus(altered_text)
negative_valid = verify_consensus(modified, cert, 3)[0]
assert negative_valid == 0, "modified document passed signature check"
print("修改后共识的匹配签名：", negative_valid)

dig = "-".join(base64.b64encode(r.microdesc).decode().rstrip("=") for r in c.relay)
md = parse_microdescriptors(download(circ, f"/tor/micro/d/{dig}", 5).decode())
assert all(r.microdesc in md for r in c.relay), "missing requested microdescriptor"
print(f"微描述符：{len(md)}；与共识 m 项匹配："
      f"{all(r.microdesc in md for r in c.relay)}")
EOF
```

## 参考输出

`valid-after` 到 `fresh-until` 表示共识的*新鲜期*，`valid-until` 则是另一项有效截止时间。私有网络示例中的短时间间隔并非所有 Tor 共识的固定有效期。

**安全边界：**本教学验证器只根据同一目录服务提供的证书检查共识的 RSA 签名，**没有**将证书绑定到预先可信的权威身份密钥，也没有验证证书签名、交叉认证、证书过期时间或共识的时间有效性。因而多数签名匹配**不能证明**共识真正来自可信的 Tor 权威节点。这里并未完成整条信任链。



以下是私有网络的历史示例输出，具体数值不保证一致。

```text
共识：5961 字节； 2026-09-24 16:01:20 -> 2026-09-24 16:01:40
方法 36；签名 3；证书 3
  test000a 127.0.0.1:5100 w=20 flag=['Authority', 'Fast', 'Guard', 'HSDir']...
  test005r 127.0.0.1:5105 w=4096 flag=['Fast', 'Guard', 'HSDir', 'Running']...
匹配签名：3（需要：2）
修改后共识的匹配签名：0
微描述符：8；与共识 m 项匹配：True
```

如何解读：

- 私有网络共识有效期为**40 秒**，即两个 20 秒投票周期。公共网络使用更长的有效期；缩短时间方便实验。
- **三台权威节点的三个签名都有效，两份已经足够。** 接受条件是严格多数。
- 修改共识后得到 **`valid signatures: 0`**，是本实验最重要的结果。永远不会失败的验证器，实际上没有验证任何东西。
- 每份微描述符的 SHA-256 摘要与共识中的对应 `m` 项匹配，**但还不能据此证明权威证书的可信身份**。

## 最容易出错的细节

签名**并不覆盖整个文件**：签名范围恰好结束于字面字符串 `directory-signature ` 的最后一个空格。通过 **CollecTor** 下载的文件，开头还可能有 `@type network-status-microdesc-consensus-3 1.0` 这类注释，它**不属于已签名文档**。

若把该注释纳入摘要，所有签名都会失败，表面像密码学错误，实际却是文档边界解析错误。因此 `signed_text` 必须从真正的 network-status 文档开始，回归测试也会固定这个要求。

## 常见问题

| 现象 | 原因 |
|---|---|
| `RELAY_END NOTDIRECTORY` 或 HTTP `503` | 前者表示中继没有目录服务，后者表示目录 HTTP 服务错误。应检查实际响应及服务是否可用。 |

# 实现详解

`labs/zh-Hans/代码/torlab/directory.py` 约 230 行，负责四件事：通过电路下载目录文档、解析文档、验证签名，再将微描述符与共识对应起来。

## 通过电路下载目录文档

```python
def download(circ: Circuit, path: str, stream_id: int) -> bytes:
    """通过 BEGIN_DIR 流向末端中继的目录服务发出 HTTP/1.0 GET 请求。"""
    s = Stream(circ, stream_id)
    circ.send(RelayMessage(RelayCommand.BEGIN_DIR, stream_id, b""))
    _, msg = s._next()
    if msg.command != RelayCommand.CONNECTED:
        raise CircuitError(f"BEGIN_DIR 请求被拒绝：{msg.command}")
    s.send(f"GET {path} HTTP/1.0\r\n\r\n".encode())
    response = s.receive_all()
    header, _, body = response.partition(b"\r\n\r\n")
    state = header.split(b"\r\n")[0]
    if b" 200 " not in state:
        raise CircuitError(f"{path}: {state.decode()}")
    return body
```

`BEGIN_DIR` 请求的是最后一跳的目录服务，不是外部 TCP 连接。客户端**必须**发送空消息体，中继**必须**忽略收到的消息体。成功时服务器**必须**发送空消息体的 `CONNECTED`，客户端**必须**忽略响应体。没有目录服务时可能返回 `RELAY_END NOTDIRECTORY`，而非 HTTP `503`。

这里的单跳电路是明确的**非匿名目录访问示例**。Tor 允许用于公开目录，但并不要求所有目录请求都使用单跳；onion 服务描述符还有其他匿名要求。

```python
circ = build([relay("000a")], cc=False)
```

这里的**单跳电路**不协商拥塞控制，是 Tor 允许的非匿名目录访问方式之一，并不是所有 Tor 目录请求都必须遵循的模式。

> 这种简化适用于共识等公开目录文档，**不适用于洋葱服务描述符**。对后者来说，请求者匿名性很重要，HSDir 会拒绝不合适的单跳访问方式；参见[实验 8](实验-08-洋葱服务.md)。

## netdoc 格式

`items` 是处理预期 netdoc 输入的教学解析器，不是完整的恶意输入安全校验器。例如截断的 PEM 区块可能抛出异常。

```python
def items(text: str) -> list[Item]:
    """将 netdoc 格式文档拆分为条目（dir-spec，netdoc）。"""
    output, lines, i = [], text.split("\n"), 0
    while i < len(lines):
        line = lines[i]
        i += 1
        if not line:
            continue
        keyword, *arguments = line.split(" ")
        object_text = None
        if i < len(lines) and lines[i].startswith("-----BEGIN "):
            j = i
            while not lines[j].startswith("-----END "):
                j += 1
            object_text = "\n".join(lines[i:j + 1]).encode()
            i = j + 1
        output.append(Item(keyword, arguments, object_text))
    return output
```

Tor 目录文档——共识、投票、中继描述符、微描述符以及权威证书——共享简单的元格式：关键字、空格分隔的参数，以及可能位于后续行中的 PEM 类对象。因此，一个小型通用 `items` 解析器便可以作为所有具体文档解析器的基础。

`parse_consensus` 则像简单状态机：`r` 行开始一台中继的记录，`s`、`w`、`p`、`m` 填入其属性。`r` 包含昵称、身份、地址和端口；`w` 存储带宽；`m` 是微描述符摘要。

## 签名边界与最容易算错的一个字节

真实函数从 `network-status-version ` 开始，跳过 CollecTor `@type` 注释，并在第一处 `directory-signature ` 后结束。RSA 摘要匹配**不能证明**权威证书的可信来源与有效期。

```python
def signed_text(text: str) -> bytes:
    """共识签名覆盖的区域：从 network-status-version 开始，
    直到 directory-signature 关键字之后的空格（dir-spec，directory-signature）。

    CollecTor 下载文件可能以 @type 注释开头；它不属于已签名文档，
    计算摘要前必须去除。
    """
    start = text.index("network-status-version ")
    pos = text.index("\ndirectory-signature ") + len("\ndirectory-signature ")
    return text[start:pos].encode()
```

签名**不覆盖整份文档**，而是包含 `directory-signature` 关键字及其后空格为止的内容。多一个或少一个字节，摘要都会改变。

使用 **CollecTor** 时尤其要留意：归档文件可能以以下内容开始：

```text
@type network-status-microdesc-consensus-3 1.0
network-status-version 3 microdesc
```

`@type` 行是归档系统添加的元数据，**不是签名范围的一部分**。如果把它算进去，所有签名都会一起失败。与其猜测九把权威密钥同时出现问题，不如首先检查文档边界。

```python
def verify_signature(consensus: Consensus, signature: Signature, cert: AuthorityCertificate) -> bool:
    """签名采用不包含算法标识符的 RSA PKCS#1 v1.5 摘要格式；
    从签名中恢复摘要，再与本地计算值比较。"""
    h = hashlib.sha256 if signature.algorithm == "sha256" else hashlib.sha1
    expected = h(signed_text(consensus.text)).digest()
    try:
        recovered = cert.signing_key.recover_data_from_signature(
            signature.signature, padding.PKCS1v15(), None)
    except Exception:
        return False
    return recovered == expected
```

在 Tor 的历史 RSA 签名格式中，使用算法参数 `None` 的 `recover_data_from_signature` 会恢复被签入的摘要，而不强制要求常规 ASN.1 DigestInfo 结构。这符合目录规范的历史签名构造。因此，某些期望标准编码算法标识符的高级 `verify()` 接口，反而可能拒绝有效的 Tor 签名。

哈希算法由签名元数据决定。现代共识签名使用 SHA-256；在网络格式允许的条件下，解析器仍可识别声明 SHA-1 的旧式格式。

这里无须使用常量时间比较，因为预期摘要和已签名文档都是公开的。相比之下，实验 3 中 ntor-v3 的 `AUTH` 与秘密派生的认证状态有关，应该使用 `hmac.compare_digest`。

## 摘要关联与信任边界

真正可信的路径必须从**预置信任的权威身份密钥**开始，验证签名证书、有效期与共识签名；然后才能通过 `m` 项中的 SHA-256 关联微描述符和 `ntor-onion-key`。本教学代码只演示后续摘要关联和 RSA 签名一致性，不能用于安全地引导公共 Tor 网络。

```text
可信权威身份密钥 → 验证后的证书 → 已签署共识 → SHA-256 `m` → 微描述符 → `ntor-onion-key`
```

## 负面测试

这些断言确认签名字节确实被修改，并且简化 RSA 验证器能够发现篡改；它们无法验证权威身份信任根。

```python
import re
bandwidth = re.search(r"Bandwidth=(\d+)", text)
assert bandwidth is not None, "missing Bandwidth field"
altered_text = text.replace(bandwidth.group(0), f"Bandwidth={int(bandwidth.group(1)) + 1}", 1)
assert altered_text != text
altered = parse_consensus(altered_text)
assert verify_consensus(altered, cert, 3)[0] == 0
```

永远返回成功的验证器毫无意义。修改一个数字并观察有效签名数降为零，能区分真正验证签名的代码与无条件通过的代码。

测试刻意不把 `Bandwidth=4096` 等值写死：私有网络中的测量带宽会变化。若硬编码的值不存在，`replace` 就什么也不会修改，负面测试可能表面通过但其实未进行任何检查。活动网络示例和意大利语 `lab6` 验证器均动态搜索带宽字段；另一个使用固定测试文件的单元测试则可以替换其已知的 `Bandwidth=4096` 值。

## 实践注意事项

- **并非所有中继都提供目录服务。** 没有目录服务的中继可返回 `END NOTDIRECTORY`，而提供服务的节点也可能返回 HTTP `503`。私有网络中可选择 `000a`、`001a` 或 `002a`。
- 私有网络共识有意设置较短有效期，切换期间获取可能出现难以解释的中间状态，等下一次投票再试。
- 微描述符共识与完整共识是**不同文档类型**，中继行格式不同，但签名验证原理相同。
- 微描述符请求路径为 `/tor/micro/d/<用减号连接的摘要>`，摘要采用末尾不含 `=` 的 base64 编码。
