## Цель работы

**Часть** статистики [Tor Metrics](https://metrics.torproject.org/) можно восстановить из открытого консенсуса: количество ретрансляторов, их флаги и согласованные значения пропускной способности. **Число пользователей нельзя вывести из одного консенсуса.** Для его оценки требуются агрегированные статистические сведения о запросах к серверам каталогов из *extra-info*-дескрипторов, поправка на долю охваченных запросов и предположение об их частоте. Полученный результат описывает **среднее присутствие клиентов за сутки**, а не точное количество разных людей.

## Подготовка

Как и в [лабораторной работе 7](Лабораторная-07-Маршруты.md), нужен консенсус за **23 сентября 2026 года, 15:00 UTC**. Исходный файл **не включён в Git**. Из корня репозитория выполните загрузку конкретного документа из архива CollecTor:

```bash
make -C labs/ru data
```

После этого предполагается файл `labs/ru/данные/collector/consensus-microdesc-2026-09-23-15`. Проверьте его заголовок, дату и происхождение. Для проверки подписей потребуются также сертификаты подписывающих ключей, **действовавшие на указанную дату**. Историческая инструкция выглядит так:

```bash
curl -o labs/ru/данные/collector/certs 'https://collector.torproject.org/recent/relay-descriptors/certs'
```

**Предупреждение:** ссылка `recent` может предоставить другие ключи, не подходящие к архивному консенсусу. Это не надёжный способ получить сертификаты на сентябрь 2026 года; при необходимости найдите их в архиве соответствующего периода. Убедитесь, что вместо сертификатов не сохранена HTML-страница или ответ об ошибке. Первый значимый заголовок — `dir-key-certificate-version 3`; документы с аннотациями CollecTor могут начинаться со строки `@type ...`.


Имена флагов оставлены на английском языке: это **значения протокола**, тогда как подписи полей вывода соответствуют русскому скрипту.

При чтении результатов необходимо учитывать следующее:

- Флаг `Exit` встречается у **3177** ретрансляторов старого снимка, но функция `exit_bandwidth_share` считает вес только узлов с `Exit` **без `BadExit`**. Примерно **33%** и **70%** представляют доли суммы значений **`Bandwidth=` из консенсуса**, **не доли реально переданного трафика и не итоговые вероятности выбора узла в цепочку**. Роли выхода и охранного узла могут пересекаться; правила взвешивания по позиции рассматриваются в [лабораторной работе 7](Лабораторная-07-Маршруты.md).
- В старом снимке **10** ретрансляторов имели флаг `Authority`, а проверка подписей использовала **9** идентификаторов голосующих центров каталогов. **Счётчик флага не является списком подписантов.** Определять по одному лишь отличию на единицу, какой именно узел был мостовым центром каталогов, нельзя: требуются архивные идентификаторы.
- `BadExit` и `MiddleOnly` ограничивают роли ретранслятора. **Сами по себе эти флаги не доказывают** вредоносное поведение или компрометацию узла.
- В отдельных диапазонах IPv4 **/16** сосредоточены сотни ретрансляторов. Это **не доказывает общего владельца** и не означает, что все они являются выходными узлами. Ограничение по /16 — лишь часть правил формирования цепочки.

Счётчики отсортированы по убыванию значений, а при равенстве — по имени. Это обеспечивает воспроизводимый порядок вывода независимо от порядка обхода множеств Python.

## Пример расчёта пользовательской оценки

```bash
python3 - <<'EOF'
from torlab.metrics import estimate_users, remove_rounding
print(estimate_users(20_000_000, 0.6))  # условные 20 млн учтённых запросов и охват 60%
EOF
```

```text
3333333
```

Этот результат — **арифметический пример на условных входных данных**:
`floor(20_000_000 / 0.6 / 10) = 3_333_333`. Консенсус **не содержит** указанные 20 миллионов запросов. Tor Metrics берёт агрегированные числа запросов из *extra-info*-дескрипторов, делит их на долю охвата `frac` и предполагаемые **10 запросов к каталогу на одного среднего клиента за сутки**. При `frac < 0.10` или `frac > 1.10` функция возвращает `None`; небольшое превышение 100% предусмотрено методикой. Округление исходных опубликованных счётчиков защищает приватность; отдельная функция `remove_rounding` **не вызывается автоматически** в данном примере. Получается не число уникальных физических лиц, а средняя оценка клиентского присутствия.

## Проверка цифровых подписей консенсуса

```bash
python3 - <<'EOF'
from torlab.directory import parse_consensus, parse_certificates, verify_consensus
c = parse_consensus(open("labs/ru/данные/collector/consensus-microdesc-2026-09-23-15").read())
cert = parse_certificates(open("labs/ru/данные/collector/certs").read())
print(verify_consensus(c, cert, 9)[:2])
EOF
```

```text
(9, 5)
```

Пара `(9, 5)` — **исторический эталонный результат**: девять распознанных действительных подписей и порог пять. В текущей ревизии его **не перепроверяли**, поскольку публичный архивный консенсус и соответствующие сертификаты не входят в Git. Результат `(0, 5)` может быть вызван загрузкой HTML, несовпадением **периода действия или идентификаторов подписывающих ключей** либо неверными границами подписанных байтов. Служебная аннотация CollecTor `@type ...` не входит в подписанную часть документа.

## Автоматическая проверка

Итальянская функция `scripts/verify_labs.py::lab15` сравнивает число ретрансляторов и доли весов из **фиксированного** старого консенсуса, проверяет арифметику условного примера и, если сертификаты присутствуют, сверяет подписи. Она **не оценивает реальное число нынешних пользователей**.

## Возможные проблемы

- **`valid signatures: (0, 5)`**: проверить аннотацию `@type`, отсутствие HTML-страницы вместо сертификатов, даты действия и ключи подписантов.
- **Статистика отличается от образца**: сравните точную дату и содержимое архивного консенсуса — числа относятся только к одному историческому снимку.
- **Файл не найден**: выполните `make -C labs/ru data`; загрузка требует сети, но сами расчёты — нет.
