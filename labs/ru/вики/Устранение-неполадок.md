# Устранение неполадок

Каждый пункт на этой странице описывает проблему, реально встречавшуюся при подготовке книги, и установленную тогда причину. Это исторические случаи из эталонного издания, **а не гарантия неизменности причин**. Лаборатория использует Docker `--network host`; порты совпадают с другими языковыми средами.

## Сеть не запускается

**`docker: Error response from daemon: Conflict. The container name "torbook-network" is already in use`**  
Контейнер уже существует, возможно он остановлен. Проверьте `docker ps -a` и убедитесь, что `torbook-network` принадлежит **одноразовой лабораторной сети**, прежде чем выполнять `make -C labs/ru/лаборатория stop`. EN/RU/ZH-CN используют одно имя контейнера; не удаляйте чужую работающую среду.

**Начальная загрузка не завершается; узлы остаются на 5%**  
Возможны конфликт портов, недоступность центров каталогов или процессы от предыдущего запуска. **Не выполняйте `pkill -x tor` без проверки:** он завершит все процессы с таким именем внутри контейнера. Сначала выполните безопасную диагностику:

```bash
docker ps -a
ss -ltnp | grep -E ':(510[0-9]|710[0-9]|800[0-9]|900[0-9])' || true
```

Убедившись, что `torbook-network` — только ваша одноразовая русская лаборатория, выполните `make -C labs/ru/лаборатория stop` и затем `make -C labs/ru/лаборатория start`. Команда `pkill -f "tor -f"` может затронуть собственную оболочку, а `pkill -x tor` — другие узлы.

**Узлы выглядят запущенными, но не отвечают**  
После аварийного завершения могут остаться устаревшие файлы `pid`. Из корня репозитория, **только после проверки того, что все ключи и результаты можно удалить**, полностью очистите и заново запустите русскую лабораторную сеть:

```bash
make -C labs/ru/лаборатория clean
make -C labs/ru/лаборатория start
```

`clean` **уничтожает содержимое `labs/ru/лаборатория/net/`**, включая закрытые ключи и идентификаторы onion-сервисов. Chutney использует две фазы; клиент и onion-сервис запускаются во второй. Итальянская цель `make riavvia` не управляет русским контейнером.

**`chutney verify` завершается с `Address already in use`**  
Возможны оставшиеся HTTP-серверы на 8080/4747 или другая языковая сеть на диапазонах ORPort, ControlPort и SOCKS. Проверьте владельца порта до остановки процессов.

```bash
ss -ltnp | grep -E ':(8080|4747|9008)'
```

## Различие между автономными тестами и проверкой сети

```bash
PYTHONPATH=labs/ru/код python3 -m pytest -q labs/ru/код/torlab/test
```

Эти тесты используют Python и сохранённые фикстуры, **не запускают сервер на порту 8080 или сеть Tor**. `make -C labs/ru/лаборатория verify` проверяет активную топологию посредством Chutney. Итальянский `make verifica-lab` запускает дополнительные проверки в **другой сети** `лаборатория/` и не сертифицирует русскую версию. Ошибка `cannot bind port 8080` относится к работающему сетевому эксперименту или серверу, а не к обычному набору фикстур pytest.

**Не проходят сетевые лабораторные работы**  
Проверьте `make -C labs/ru/лаборатория status`, затем журналы `000a/notice.log` и `008c/notice.log`, если они существуют. Автономный pytest не требует работающей сети.

**Одна лабораторная работа падает один раз, а при повторе проходит**  
В сети всего несколько relay, поэтому построение цепи иногда может не удаться с первой попытки. `CREATE2 rejected (command 4)` означает, что пришла ячейка `DESTROY`. После сохранения журналов можно повторить попытку, но успешный повтор **не доказывает правильности**: непостоянные ошибки также требуют диагностики.

**Только лабораторные работы 7, 15 и 19 не проходят численные проверки**  
Эти численные сравнения выполняет **итальянский корневой проверяющий скрипт** с консенсусом от 23 сентября 2026 года в `fonti/collector/`, **не русский pytest**. При отсутствии файла итальянский проверяющий сообщает **SKIP, а не PASS**. Для отдельного анализа русских данных сначала используйте `make -C labs/ru data`; фикстуры pytest не заменяют исторический консенсус.

## Отдельные лабораторные работы

**Onion-сервис перестаёт отвечать; в журналах `400 Invalid HS descriptor`**  
В исходном эксперименте наблюдалась пустая папка `authorized_clients`, но сообщение `400` не является универсальной диагностикой. **Пустая папка не активирует авторизацию клиентов**: Tor должен успешно прочитать хотя бы один корректный файл `.auth` с записью `descriptor:x25519:<публичный-ключ-base32>`. Без активированной защиты сервис может быть доступен всем, кто знает адрес. Если [лабораторная работа 13](Лабораторная-13-Ограниченное-обнаружение.md) прервалась, сначала без удаления файлов осмотрите `restricted_service/authorized_clients` и соответствующий `torrc`. Обновлённый скрипт посылает HUP **проверенному PID** конкретного узла и при сбое восстановления сохраняет временные ключи. Не используйте `pkill -HUP -f` и не удаляйте каталоги вслепую.

В этой одноразовой *тестовой* сети проще всего восстановить исходное состояние очисткой и новым запуском:

```bash
make -C labs/ru/лаборатория clean
make -C labs/ru/лаборатория start
```

**Предупреждение:** `clean` удаляет сгенерированные тестовые ключи и состояние `labs/ru/лаборатория/net/`. Никогда не применяйте подобную процедуру к настоящему onion-сервису.

**Лабораторный клиент завершается после изменения torrc**  
Параметр вроде `ClientOnionAuthDir` или `HiddenServiceDir` содержит путь **хоста**, тогда как tor читает его **внутри** контейнера. Это приводит к ошибке конфигурации. Выводите контейнерные пути из `DataDirectory` соответствующего узла.

**Выходной ретранслятор отвечает `END TORPROTOCOL` на каждый запрос**  
Используется **одношаговая цепь**. Выходной ретранслятор не пересылает обычный исходящий трафик из такой цепи, чтобы не стать открытым прокси. Постройте лабораторную цепь из трёх ретрансляторов.

**`LookupError: no microdescriptor for 003r`**  
Клиент ещё не загрузил микродескрипторы. После запуска сети подождите примерно минуту и проверьте обновление каталога.

**`the relay has a different identity from the expected one`, хотя порт правильный**  
Сеть была создана заново и получила новые ключи. Каждый `make -C labs/ru/лаборатория clean` меняет идентификаторы всех узлов. Снова прочитайте `fingerprint-ed25519`.

**pcap пуст либо `tshark` ничего не расшифровывает**  
Возможные причины **без доказанного порядка частоты**: поздний старт захвата, отсутствие прав у `tcpdump` или установка `SSLKEYLOGFILE` уже после создания TLS-сокета. Не каждая реализация TLS экспортирует ключевой материал для расшифровки.

## Восстановление исходного состояния

Лабораторная сеть одноразовая. Если состояние стало трудно диагностировать, проще начать заново:

```bash
make -C labs/ru/лаборатория clean
make -C labs/ru/лаборатория start
make -C labs/ru/лаборатория verify
PYTHONPATH=labs/ru/код python3 -m pytest -q labs/ru/код/torlab/test
```

Значения `successes:4 failures:0` и `53/53` относятся **только к исторической эталонной проверке**: результаты текущей русской среды необходимо наблюдать, а не предполагать.

**Предупреждение:** `clean` удаляет сгенерированные данные и тестовые ключи в `labs/ru/лаборатория/net/`. Перед использованием убедитесь, что каталог содержит только одноразовое состояние этой лабораторной сети.

## Если проблема не перечислена

У каждого узла есть журнал `labs/ru/лаборатория/net/nodes/<node>/notice.log`; особенно полезен журнал клиента. Для более подробной диагностики изучите `info.log`, если узел настроен на его запись.

Когда экспериментальный результат не совпадает с ожиданием, полезно найти промежуточную контрольную точку и сравнить её с эталонной реализацией. Клиент `tor` внутри лаборатории имеет ControlPort, отвечает на `GETINFO` и реализует почти всё, что пытается делать наш экспериментальный клиент, но значительно лучше протестирован.
