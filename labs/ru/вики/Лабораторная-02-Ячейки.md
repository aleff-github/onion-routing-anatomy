## Что демонстрирует эта работа

**514 байт** относятся к фиксированным ячейкам link protocol 4 и выше; версия 3 использует CircID длиной 2 байта и ячейки по 512 байт.

Ячейка Tor имеет простой жёсткий формат: 4 байта CircID, 1 байт команды и 509 байт body — **всего 514 байт** независимо от содержимого. Такая унификация не позволяет длине ячейки напрямую раскрывать её тип содержимого. Исключение — ячейки переменной длины (`VERSIONS` и все команды >= 128). `VERSIONS` всегда использует двухбайтовый CircID, потому что передаётся до согласования версии link protocol.

## Запуск эксперимента

```bash
python3 - <<'EOF'
from torlab.cells import *

# 1. ячейка фиксированной длины
c = Cell(0x80000001, CellCommand.RELAY, b"\x01" * 509)
g = encode(c, 4)
print("length:", len(g), "| first 8 bytes:", g[:8].hex())

# 2. декодировать ячейку и оставшиеся байты
decoded_cell, remaining = decode(g, 4)
print("decoded:", hex(decoded_cell.circ_id), CellCommand(decoded_cell.command).name, "| remaining:", len(remaining))

# 3. ячейка переменной длины
print("VERSIONS:", encode(Cell(0, CellCommand.VERSIONS, b"\x00\x04\x00\x05"), 4).hex())

# 4. relay-сообщение в теле ячейки
m = RelayMessage(RelayCommand.BEGIN, 1, b"127.0.0.1:80\x00")
r = encode_relay(m)
print("relay message:", len(r), "байт | header:", r[:11].hex())
rit = decode_relay(r)
print("decoded:", RelayCommand(rit.command).name, rit.stream_id, rit.data)
EOF
```

## Ожидаемый вывод

```text
length: 514 | first 8 bytes: 8000000103010101
decoded: 0x80000001 RELAY | remaining: 0
VERSIONS: 000007000400040005
relay message: 509 байт | header: 010000000100000000000d
decoded: BEGIN 1 b'127.0.0.1:80\x00'
```

Как читать результат:

- `8000000103` — CircID `0x80000001` (старший бит равен единице, потому что цепь создали мы, initiator канала), за которым следует команда `3` (`RELAY`).
- Ячейка `VERSIONS` состоит из `0000` — **двухбайтового** CircID, `07` — команды, `0004` — длины и `0004 0005` — предложенных версий 4 и 5.
- Header relay message: `01` (`BEGIN`), `0000` (`Recognized`), `0001` (StreamID), `00000000` (Digest пока пуст; его заполнит шифрование лабораторной работы 4) и `000d` — 13 байт данных.

`Cell.command` и `RelayMessage.command` представлены целыми числами. Для символических имён преобразуйте их через `CellCommand(...)` и `RelayCommand(...)`.

# Подробности реализации

Вся работа сосредоточена в `labs/ru/код/torlab/cells.py`, примерно 220 строк. От него зависят все последующие лабораторные работы. Ошибка здесь может проявиться лишь через несколько экспериментов как цепь, которую relay закрывает без полезного объяснения.

Ниже приведены фрагменты из полного `cells.py`; импорты и вспомогательные определения нужно брать из самого модуля.

## Константы

```python
CELL_BODY_LEN = 509          # байт в body ячейки фиксированной длины
RELAY_HEADER_LEN = 11        # header relay message
RELAY_DATA_MAX = CELL_BODY_LEN - RELAY_HEADER_LEN   # 498
```

`RELAY_DATA_MAX` не скопирована из спецификации как независимое число: это **следствие** двух предыдущих размеров. Выражение через вычитание сохраняет связь видимой, если формат изменится. Такая возможность реальна: CGO relay encryption из Proposal 359 использует иной header, а Proposal 340 вообще отделяет сообщения от ячеек.

Команды представлены как `IntEnum`, а не обычный `Enum`. Для бинарного протокола это важно: значения должны сравниваться и сериализоваться как integers — например, `bytes([cell.command])` — но при этом сохранять читаемые символические имена.

```python
def circid_len(version):
    return 2 if version < 4 else 4

def is_variable_length(command):
    return command == CellCommand.VERSIONS or command >= 128
```

Ширина CircID зависит от версии link protocol: два байта до версии 3 включительно и четыре начиная с версии 4. Вынос правила в helper предотвращает рассыпание magic numbers по модулю.

Правило `>= 128` задаётся спецификацией: старший бит команды обозначает ячейку переменной длины. `VERSIONS` с командой 7 — историческое исключение.

## `encode`

```python
def encode(cell: Cell, version: int) -> bytes:
    """Сериализовать ячейку канала для link protocol `version`.

    Ячейки VERSIONS всегда кодируются с версией 0 (двухбайтовый CircID),
    поскольку при их отправке версия link protocol ещё не согласована.
    """
    if cell.command == CellCommand.VERSIONS:
        version = 0
    n = circid_len(version)
    if not 0 <= cell.circ_id < 1 << (8 * n):
        raise CellError(f"CircID {cell.circ_id:#x} не помещается в {n} байт")
    header = cell.circ_id.to_bytes(n, "big") + bytes([cell.command])
    if is_variable_length(cell.command):
        if len(cell.body) > 0xFFFF:
            raise CellError("body слишком велико для ячейки переменной длины")
        return header + struct.pack(">H", len(cell.body)) + cell.body
    if len(cell.body) > CELL_BODY_LEN:
        raise CellError(f"body длиной {len(cell.body)} байт > {CELL_BODY_LEN}")
    # Дополнить нулями до CELL_BODY_LEN (tor-spec, body-padding).
    return header + cell.body.ljust(CELL_BODY_LEN, b"\x00")
```

Первые две строки — важный special case. `VERSIONS` обменивается *до* согласования link version, поэтому её формат не может зависеть от результата этого согласования. Принудительное `version = 0` даёт двухбайтовый CircID, как требует спецификация.

`"big"` означает network byte order, используемый для integer fields Tor. Явная проверка диапазона CircID технически не обязательна — `to_bytes` сам вызвал бы `OverflowError`, — но собственная ошибка сообщает, какое значение не помещается и сколько байт было доступно.

Два семейства ячеек расходятся здесь:

- **Переменная длина:** записать двухбайтовый `Length`, затем body ровно заданной длины. Fixed-size padding не нужен.
- **Фиксированная длина:** дополнить body нулями до **509 байт**. Получатель игнорирует добавленные байты.

> Padding фиксированной ячейки относится к уровню канала: непосредственный TLS-сосед видит его после расшифрования, но внешний наблюдатель нет. Padding relay-сообщения защищён onion-шифрованием до узла-получателя.

## `decode`

**Особенность `VERSIONS` при чтении:** до согласования версии следует вызывать `decode(buffer, 0)`, чтобы CircID был двухбайтовым. После согласования вызывайте `decode(buffer, negotiated_version)` для остальных ячеек; передавать 4 для начальной `VERSIONS` неверно.

```python
def decode(buffer: bytes, version: int) -> tuple[Cell, bytes] | None:
    """Извлечь первую ячейку из `buffer`.

    Вернуть (cell, remaining_bytes) либо None, если buffer ещё не содержит
    полную ячейку: TLS-данные могут приходить фрагментами произвольного размера.
    """
    n = circid_len(version)
    if len(buffer) < n + 1:
        return None
    circ_id = int.from_bytes(buffer[:n], "big")
    command = buffer[n]
    if is_variable_length(command):
        if len(buffer) < n + 3:
            return None
        (length,) = struct.unpack(">H", buffer[n + 1:n + 3])
        end = n + 3 + length
        body_start = n + 3
    else:
        end = n + 1 + CELL_BODY_LEN
        body_start = n + 1
    if len(buffer) < end:
        return None
    return Cell(circ_id, command, buffer[body_start:end]), buffer[end:]
```

Функция вызывается при поступлении байтов из socket даже тогда, когда caller ещё не знает, пришла ли целая ячейка. Поэтому она имеет **три** отдельных проверки полноты:

1. Без CircID и command нельзя определить формат ячейки.
2. Для variable-length cell нужны ещё два байта, прежде чем станет известна длина body.
3. Наконец, должен полностью прибыть сам body.

Возврат `None` означает «вызови меня снова, когда придут дополнительные байты», а не protocol error. Поэтому caller остаётся простым:

```python
while True:
    result = decode(buffer, version)
    if result is None:
        chunk = sock.recv(4096)
        if not chunk:
            raise EOFError("connection closed before a complete cell")
        buffer += chunk
        continue
    cell, buffer = result
    ...
```

Границы TLS-записи и cell независимы: данные могут приходить частями или по несколько cell за раз. В 16 KiB могут поместиться 31 целая cell по 514 байт, но это не обязательное число.

Учебный клиент использует immutable `bytes` и каждый раз создаёт slice остатка. Production-реализация применяет более эффективный буфер, чтобы не копировать данные при каждом извлечении.

## `negotiate_version`

```python
def negotiate_version(ours: list[int], received_body: bytes) -> int:
    """Выбрать наибольшую версию, поддерживаемую обеими сторонами (tor-spec, VERSIONS-cells)."""
    if len(received_body) % 2:
        raise CellError("VERSIONS содержит нечётное число байтов")
    theirs = {v for (v,) in struct.iter_unpack(">H", received_body)}
    common = set(ours) & theirs
    if not common:
        raise CellError("нет общей версии link protocol")
    return max(common)
```

Body нечётной длины не может быть списком двухбайтовых integers, поэтому он отклоняется. Затем вычисляется пересечение множеств и выбирается **наибольшая** общая версия, как требует спецификация.

Что мешает downgrade-атаке, где посредник удаляет новые версии из списков? Сам helper этого не определит. Защита приходит из окружающего channel protocol:

- обмен уже идёт внутри TLS, а [лабораторная работа 1](Лабораторная-01-Канал.md) привязывает канал к identity relay через `CERTS`;
- когда initiator сам является relay и аутентифицируется, digest `AUTHENTICATE` покрывает **все** переданные байты, включая `VERSIONS`, поэтому изменение обнаруживается.

## `encode_relay`

```python
def encode_relay(msg: RelayMessage, random_bytes=os.urandom) -> bytes:
    """Сформировать 509-байтовое plaintext body ячейки RELAY.

    Padding: 4 нулевых байта, затем случайные байты (tor-spec, relay-cell-padding).
    Digest вычисляется отдельно (глава 10); эта функция использует значение из `msg`.
    """
    if len(msg.data) > RELAY_DATA_MAX:
        raise CellError(f"в ячейке допускается не более {RELAY_DATA_MAX} байт data")
    header = struct.pack(">BHH4sH", msg.command, msg.recognized,
                               msg.stream_id, msg.digest, len(msg.data))
    space = CELL_BODY_LEN - RELAY_HEADER_LEN - len(msg.data)
    padding = b"\x00" * min(4, space) + random_bytes(max(0, space - 4))
    return header + msg.data + padding
```

Один `struct.pack` сериализует все пять полей header. Формат `">BHH4sH"` читается слева направо как схема главы 8: command — 1 байт, `Recognized` — 2, StreamID — 2, Digest — 4 raw bytes, `Length` — 2. Итого 11 байт, то есть `RELAY_HEADER_LEN`.

Спецификация рекомендует (**SHOULD**) до четырёх начальных нулевых байтов и случайные байты после них. Если место меньше четырёх байтов, все оставшиеся байты равны нулю. Само заполнение не служит проверкой распознавания: нужны `Recognized` и `Digest`.

| | Fixed-length cell | Relay message |
|---|---|---|
| Padding | Только нули | До 4 нулей, затем случайные байты при наличии места |
| Кто видит plaintext | Непосредственный TLS-сосед, не внешний наблюдатель | Узел, распознавший и расшифровавший relay-сообщение |
| Цель | Заполнить фиксированный body | Сделать неиспользуемую часть relay body непредсказуемой |

Если бы relay-message padding состоял только из нулей, атакующий, угадавший полезную нагрузку, знал бы и весь оставшийся body. Это плохо сочетается с authenticated `SENDME` из Proposal 289 ([лабораторная работа 5](Лабораторная-05-Потоки.md)). Спецификация рекомендует (**SHOULD**) до четырёх начальных нулевых байтов и случайные байты после них. Если место меньше четырёх байтов, все оставшиеся байты равны нулю. Само заполнение не служит проверкой распознавания: нужны `Recognized` и `Digest`.

Параметр `random_bytes` существует ради тестов: случайный источник можно заменить предсказуемым. Это общий принцип репозитория — **внедрять nondeterminism как зависимость, а не прятать его внутри реализации**.

Процедура распознавания и проверки digest на уровне onion показана в [лабораторной работе 4](Лабораторная-04-Шифрование.md).
