## Что демонстрирует эта работа

На практике «луковица» устроена так: для каждого узла цепи и каждого направления используются отдельный ключ шифрования и накопительный хеш. Клиент оборачивает сообщение в число слоёв, соответствующее расстоянию до узла назначения. Промежуточный ретранслятор заранее не знает, предназначена ли ячейка ему или должна быть передана дальше: он снимает свой слой, пытается распознать сообщение и, если проверка не проходит, пересылает результат.

Главная цель — поэтапно построить цепь, добавляя по одному узлу до выходного ретранслятора.

## Запуск эксперимента

```bash
python3 - <<'EOF'
import time
from torlab.cells import CellCommand
from torlab.circuit import build
from torlab.laboratory import relay

circ = build([relay("003r"), relay("004r"), relay("006e")])
print("переходов:", len(circ.crypto.hops), "| расширения, запрошенные у выходного узла:", circ.exit_extensions)

# заполнение канала, не наблюдавшееся в примере лабораторной работы 1
circ.channel.sock.settimeout(12)
seen, t = 0, time.time()
try:
    while time.time() - t < 12:
        if circ.channel.receive().command == CellCommand.PADDING:
            seen += 1
except TimeoutError:
    pass
print(f"PADDING-ячеек получено за 12 с: {seen}")
EOF
```

## Ожидаемый вывод

```text
переходов: 3 | расширения, запрошенные у выходного узла: [(2, b'\x1f')]
PADDING-ячеек получено за 12 с: 3
```

Как читать результат:

- `build` открывает канал к сторожевому узлу, создаёт первый переход с помощью ntor-v3 и дважды расширяет цепь. `EXTEND2` использует **StreamID 0**, поскольку это сообщение управления цепью. Оно передаётся внутри `RELAY_EARLY`, а не `RELAY`; именно это позволяет ограничить число расширений восемью такими ячейками ([лабораторная работа 17](Лабораторная-17-Relay-early.md)).
- В данном примере управление перегрузкой запрашивается **только у последнего узла**. `[(2, b'\x1f')]` — ответ exit с `sendme_inc = 31`.
- **Добавление `PADDING` зависит от конфигурации и времени.** Продление цепи за первый ретранслятор может сделать канал пригодным для заполнения, но количество пакетов в приведённом выводе лишь пример; за двенадцать секунд их может быть ноль.

## Ядро лабораторной работы

Сама onion-обработка сводится к двум циклам:

```python
def encrypt(self, msg: RelayMessage, destination: int | None = None) -> bytes:
    d = len(self.hops) - 1 if destination is None else destination
    body = self.hops[d].forward.sign(encode_relay(msg))
    for i in range(d, -1, -1):
        body = self.hops[i].forward.apply(body)
    return body

def decrypt(self, body: bytes) -> tuple[int, RelayMessage]:
    for i, hop in enumerate(self.hops):
        body = hop.backward.apply(body)
        if hop.backward.recognizes(body):
            return i, decode_relay(body)
    raise CellError("ячейка не распознана ни одним hop: circuit следует закрыть")
```

`recognizes` сложнее, чем кажется. Поле `Recognized` должно быть равно нулю, **а накопительный хеш — совпасть**. При неудачной проверке нельзя изменять действительное состояние хеша, иначе ложное срабатывание нарушит синхронизацию цепи. Поэтому реализация проверяет копию (`self.digest.copy()`) и принимает её только после успешной верификации.

Приведены фрагменты методов `ClientCircuitCrypto` и `Circuit`; необходимые импорты, типы и состояние определены в полных модулях Python.

## Ограничение in-memory-тестов

`test_encryption.py` строит смоделированную трёхузловую цепь и проверяет, что каждый hop распознаёт только собственные сообщения, middle-relay видит байты, похожие на случайные, изменение данных обнаруживается у адресата, а AES-CTR остаётся malleable.

Но у такого теста есть серьёзное ограничение: simulated client и relay используют **одну и ту же реализацию**. Если обе стороны одинаково неверно обновляли digest, тест всё равно мог бы пройти. Поэтому сильнейшая проверка — interoperability с независимой реализацией `tor`, что и делает эта лабораторная работа.

# Подробности реализации

Участвуют два модуля: `labs/ru/код/torlab/encryption.py` — собственно onion-механизм, около 115 строк, — и `labs/ru/код/torlab/circuit.py`, связывающий channel, CircID и hops, тоже около 115 строк.

## Что хранит `Direction`

```python
POS_DIGEST = slice(5, 9)
POS_RECOGNIZED = slice(1, 3)

def _aes_ctr(key):
    return Cipher(algorithms.AES(key), modes.CTR(bytes(16))).encryptor()

def _without_digest(body):
    return body[:5] + bytes(4) + body[9:]
```

**IV равен нулю**, и это не упрощение. В Tor CTR state продолжается от ячейки к ячейке на протяжении жизни цепи, поэтому keystream не начинается заново для каждой ячейки. Повторная инициализация cipher на каждой ячейке повторно использовала бы keystream и катастрофически ослабила шифрование.

```python
@dataclass
class Direction:
    cipher: object
    digest: "hashlib._Hash"
```

`Direction` объединяет два состояния, которые должны продвигаться согласованно: AES-CTR cipher state и running digest. В спецификации они описаны отдельно, но в реализации тесно связаны. У каждого hop два направления — forward и backward, поэтому трёхузловая цепь хранит шесть объектов `Direction`.

## Шифрование и расшифрование — один primitive

```python
def apply(self, data):
    return self.cipher.update(data)
```

В CTR mode и encryption, и decryption — XOR с keystream. Именно поэтому middle-relay «снимает слой» тем же primitive.

Следствие — AES-CTR **malleable**: изменение бита ciphertext меняет соответствующий бит plaintext. Running digest обнаруживает такую модификацию; приложение B книги показывает это свойство отдельно.

## Digest не относится к одной ячейке

```python
def sign(self, body):
    self.digest.update(_without_digest(body))
    return body[:5] + self.digest.digest()[:4] + body[9:]
```

Накопительный digest охватывает **только relay-ячейки, исходящие от данного узла или адресованные ему в этом направлении**, но не пересылаемые другим узлам. `update` накапливает состояние, поэтому каждое принятое сообщение зависит от всей предыдущей истории.

Последовательность такова: очистить поле Digest через `_without_digest`, обновить running hash, взять первые четыре байта результата и записать их в поле Digest. Получатель выполняет то же вычисление.

Практическое следствие: **потеря или перестановка relay cell навсегда рассинхронизирует running state**. Tor не пытается восстановить его и закрывает цепь.

Обычные circuits используют SHA-1 для running digest, тогда как onion-service circuits используют SHA3-256. Применение SHA-1 здесь связано с конкретной protocol construction, а не с обычными требованиями collision resistance.

## Recognition и копия, защищающая цепь

```python
def recognizes(self, body):
    if body[POS_RECOGNIZED] != b"\x00\x00":
        return False
    candidate = self.digest.copy()
    candidate.update(_without_digest(body))
    if candidate.digest()[:4] != body[POS_DIGEST]:
        return False
    self.digest = candidate
    return True
```

Это самая деликатная операция модуля.

Первый фильтр — `Recognized`: если два байта не нулевые, сообщение не предназначено этому relay и digest state не трогается.

Но два нулевых байта могут случайно возникнуть примерно в одном случае из 65 536. Поэтому второй фильтр — Digest. Если обновить настоящий digest до того, как выяснится, что Digest field неверен, один false positive повредит все последующие проверки.

Использование `copy()` и присваивание состояния только после успешной проверки делает failed recognition **без побочных эффектов**, что сохраняет синхронизацию цепи.

## Два onion-цикла

```python
def encrypt(self, msg: RelayMessage, destination: int | None = None) -> bytes:
    d = len(self.hops) - 1 if destination is None else destination
    body = self.hops[d].forward.sign(encode_relay(msg))
    for i in range(d, -1, -1):
        body = self.hops[i].forward.apply(body)
    return body

def decrypt(self, body: bytes) -> tuple[int, RelayMessage]:
    for i, hop in enumerate(self.hops):
        body = hop.backward.apply(body)
        if hop.backward.recognizes(body):
            return i, decode_relay(body)
    raise CellError("ячейка не распознана ни одним hop: circuit следует закрыть")
```

Исходящий трафик подписывается digest целевого hop, затем оборачивается от внутреннего слоя наружу. Входящий трафик снимает слои снаружи внутрь и после каждого слоя проверяет recognition.

Обратите внимание: `decrypt` заранее не знает, какой hop создал сообщение. Он обнаруживает отправителя постепенно, снимая слои и проверяя recognition — ровно так же действует сам relay protocol.

## Расширение цепи

```python
def extend(self, r: RelayInfo, extensions=()) -> list[tuple[int, bytes]]:
    st, hd = ntor3_client_start(r.id_ed, r.ntor, encode_extensions(list(extensions)))
    body = extend2_body("127.0.0.1", r.port, r.id_rsa, r.id_ed, HTYPE_NTOR_V3, hd)
    self.send(RelayMessage(RelayCommand.EXTEND2, 0, body), early=True)
    hop, msg = self.receive()
    if msg.command != RelayCommand.EXTENDED2:
        raise CircuitError(f"расширение circuit не удалось: {RelayCommand(msg.command).name}")
    sm, k = ntor3_client_finish(st, hdata_created2(msg.data))
    self.crypto.hops.append(Hop.from_keys(CircuitKeys.from_stream(k)))
    return decode_extensions(sm)
```

Три детали часто становятся причиной непонятных ошибок:

- **StreamID 0:** `EXTEND2` управляет цепью, а не application stream.
- **`RELAY_EARLY`, а не `RELAY`:** extension requests используют специальный тип ячейки с конечным лимитом ([лабораторная работа 17](Лабораторная-17-Relay-early.md)).
- **Идентификаторы ретранслятора:** в этом примере для `EXTEND2` передаются RSA и Ed25519. Спецификация не требует Ed25519 без исключений во всех запросах `EXTEND2`; если расширяющий ретранслятор знает ключ из консенсуса, ему СЛЕДУЕТ его проверить. Отсутствие Ed25519 само по себе не означает неизбежный `DESTROY`.

В этом примере управление перегрузкой запрашивается **только у последнего узла**: расширение `(1, b"")` направляется выходному, а не промежуточному ретранслятору.

## Ограничение in-memory-тестов

`test_encryption.py` хорошо проверяет invariants, но обе simulated стороны используют один код. Symmetric bug может остаться незамеченным. Поэтому совместимость с независимой реализацией `tor` — обязательный дополнительный слой проверки.

## Что важно знать для успешного запуска

- Circuit keys берутся из ntor key stream: 20+20 байт digest (`Df`, `Db`) и 16+16 байт encryption keys (`Kf`, `Kb`), всего 72 байта. Порядок принципиален.
- **Начальное digest state** направления seeded значением `Df` или `Db`, а не пустым hash.
- Объект `Direction` нельзя повторно использовать между circuits: его CTR state постоянно продвигается.
- Если для сообщения, которое должно быть вашим, появляется `ячейка не распознана ни одним hop: circuit следует закрыть`, проверяйте все ветви, где running digest мог продвинуться ошибочно.
