## Что демонстрирует эта работа

Учебный клиент скачивает мегабайт данных через три ретранслятора и сравнивает полученный SHA-256 с исходным файлом. Во втором опыте клиент **перестаёт отправлять ячейки `SENDME`** и считает, сколько ячеек `DATA` успеет передать выходной ретранслятор до паузы. Так становится видно отличие старого управления потоком от современного управления перегрузкой.

## Запуск эксперимента

```bash
python3 - <<'EOF'
import hashlib
import time
from pathlib import Path
from torlab.circuit import build
from torlab.laboratory import relay
from torlab.stream import Stream

circ = build([relay("003r"), relay("004r"), relay("006e")])
s = Stream(circ, 1)
t = time.time()
s.open("127.0.0.1", 8080)
s.send(b"GET / HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
r1 = s.receive_all()
print(f"поток 1: {len(r1)} байт за {time.time()-t:.2f} s, DATA-ячеек {s.reg.data_cells}, "
      f"SENDME цепи {circ.sendme_sent}, прочее {s.reg.others}")

s = Stream(circ, 2)  # второй поток той же цепи
t = time.time()
s.open("127.0.0.1", 8080)
s.send(b"GET /grande.bin HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
r2 = s.receive_all()
print(f"поток 2: {len(r2)} байт за {time.time()-t:.2f} s, DATA-ячеек {s.reg.data_cells}, "
      f"SENDME цепи {circ.sendme_sent}, прочее {s.reg.others}")

headers, sep, payload = r2.partition(b"\r\n\r\n")
if not sep or b" 200 " not in headers.split(b"\r\n", 1)[0]:
    raise RuntimeError("HTTP response is missing or is not 200 OK")
reference = Path("/tmp/labweb/grande.bin").read_bytes()
assert len(reference) == len(payload) == 1048576, "HTTP file length differs"
expected_sha = hashlib.sha256(reference).hexdigest()
received_sha = hashlib.sha256(payload).hexdigest()
assert received_sha == expected_sha, "download SHA-256 does not match local file"
print("SHA-256 полученного файла:", received_sha)
print("SHA-256 совпал с локальным файлом")
EOF
```

## Ожидаемый вывод

Этот вывод — иллюстрация, а не новый результат проверки: исходный файл заполняется случайными байтами, HTTP-заголовки и список файлов меняются, а число ячеек зависит от передачи. SHA-256 вычисляется и сверяется во время выполнения.

```text
поток 1: ... DATA-ячеек 1, ... SENDME цепи 0, ...
поток 2: ... DATA-ячеек 2120, ... SENDME цепи 68, ...
SHA-256 полученного файла: <64 шестнадцатеричных символа SHA-256 созданного файла>
SHA-256 совпал с локальным файлом
```

- При успешном `BEGIN` приходит `CONNECTED`. Для IPv4 его тело может иметь длину 8 байт (адрес и TTL), но спецификация также допускает пустое тело или формат IPv6. `7f000001 00000708` — **исторический пример**, а не обязательный ответ или постоянный TTL.
Счётчик относится к ячейкам, **созданным последним узлом для потоков данной цепи**, а не ко всем транзитным ячейкам предыдущих узлов. Оба потока здесь проходят через один exit.

В иллюстративном запуске 1 + 2120 ячеек DATA при размере подтверждения 31 дают floor(2121 / 31) = 68 SENDME цепи. Это пример, а не постоянное значение. Для 1048781 HTTP-байта необходимо не менее ceil(1048781 / 498) = 2106 ячеек; 2120 показывает эффект частично заполненных ячеек.

## Ошибка, ради которой эта лабораторная работа особенно полезна

Первая реализация ошибочно хранила счётчик `SENDME` цепи внутри **отдельного потока**. Первый поток, использовавший лишь несколько ячеек, работал нормально, а передача мегабайта через второй завершалась уничтожением цепи (`DESTROY`) выходным ретранслятором.

Причина в том, что подтверждение `SENDME` уровня цепи учитывает ячейки `DATA` **всех её потоков, обслуживаемых выходным узлом**. Ретранслятор уже подсчитал ячейки первого потока и ожидал следующий `SENDME` раньше, чем рассчитывал клиент. Клиент отправлял подтверждение слишком поздно и с несовпадающим накопительным хешем. Согласно предложению 289, такое несоответствие требует закрытия цепи. Перенос счётчика в `Circuit` исправил ошибку.

Подтверждения `SENDME` уровня цепи **аутентифицированы**: они содержат накопительный хеш, соответствующий ячейке, вызвавшей подтверждение. Участник, который не обработал соответствующий трафик, не может просто подделать подтверждение и заставить отправителя передавать данные быстрее.

## Прямое наблюдение за окнами

```bash
python3 - <<'EOF'
from torlab.circuit import build
from torlab.laboratory import relay
from torlab.stream import Stream
for cc in (True, False):
    circ = build([relay("003r"), relay("004r"), relay("006e")], cc=cc)
    circ.count_received_data = lambda: None
    s = Stream(circ, 1)
    s.open("127.0.0.1", 8080)
    s.send(b"GET /grande.bin HTTP/1.0\r\n\r\n")
    circ.channel.sock.settimeout(6)
    try:
        s.receive_all()
    except TimeoutError:
        pass
    print(f"управление перегрузкой={cc}: выходной узел останавливается после {s.reg.data_cells} DATA-ячеек")
EOF
```

Следующие цифры соответствуют конкретной лабораторной сети: начальное окно перегрузки 124 ячейки (4 × `sendme_inc = 31`) и прежнее окно потока 500 ячеек. Параметры консенсуса, версия Tor и условия запуска могут повлиять на результат.

```text
управление перегрузкой=True: выходной узел останавливается после 124 DATA-ячеек
управление перегрузкой=False: выходной узел останавливается после 500 DATA-ячеек
```

**124** соответствует четырём порциям по 31 DATA-ячейке, **а не буквально четырём TLS-записям**. **500** обусловлено исчерпанием прежнего окна потока раньше номинального окна цепи в 1000 ячеек. Выходной ретранслятор прекращает формировать новые ячейки DATA, ожидая подтверждения; это не означает, что все ожидающие передачи байты уже находятся в его прикладном буфере.

Учебный класс `Stream` **не реализует SENDME уровня потока**. При согласованном управлении перегрузкой (`cc=True`) это допустимо, но при `cc=False` большой файл намеренно не удастся скачать полностью: поток остановится на окне из 500 ячеек, даже если подтверждения уровня цепи включены. Это ограничение учебного примера, а не полноценная реализация исторического режима.

# Подробности реализации

Основной код — около 80 строк в `labs/ru/код/torlab/stream.py`, а учёт `SENDME` уровня цепи находится в `circuit.py`. Здесь учебный клиент впервые переходит от демонстрации протокола к загрузке настоящих файлов.

## Открытие потока

```python
def begin_body(address: str, port: int, flag: int = 0) -> bytes:
    """Lowercase ADDRPORT с NUL-терминатором; при нуле FLAGS не передавать."""
    body = f"{address.lower()}:{port}".encode() + b"\x00"
    return body + (struct.pack(">I", flag) if flag else b"")

```

Три особенности кодирования с учётом точных нормативных формулировок:

- **Нижний регистр (SHOULD):** адрес рекомендуется передавать в нижнем регистре ради уменьшения идентифицируемости клиента; принимающая сторона **MUST** принимать и смешанный регистр.
- **Завершение нулевым байтом (NUL):** поле содержит строку с нулевым терминатором, а не префикс длины.
- **Отсутствие `FLAGS` при нуле:** необязательное поле опускается при нулевом значении; ненулевые флаги позволяют указать, например, предпочтения IPv6.

```python
def open(self, address: str, port: int) -> bytes:
    self.circ.send(RelayMessage(RelayCommand.BEGIN, self.id, begin_body(address, port)))
    _, msg = self._next()
    if msg.command == RelayCommand.END:
        raise CircuitError(f"BEGIN отклонён: {END_REASONS.get(msg.data[0], msg.data[0])}")
    if msg.command != RelayCommand.CONNECTED:
        raise CircuitError(f"неожиданный ответ на BEGIN: {msg.command}")
    return msg.data
```

У учебного клиента есть сознательное отличие от обычного Tor, влияющее на его сетевой отпечаток. Спецификация требует передавать `EXTEND2` внутри `RELAY_EARLY` и рекомендует использовать оставшийся бюджет ранних ячеек для первых примерно восьми сообщений клиента, адресованных не первому узлу. Реализация tor применяет `RELAY_EARLY` при `cpath_layer != origin_circ->cpath`, пока `remaining_relay_early_cells > 0`; всего на исходящую цепь предусмотрен бюджет до восьми таких ячеек, часть которых расходуется на расширение.

Поэтому tor обычно отправляет начальный `BEGIN` в `RELAY_EARLY`, тогда как учебный клиент применяет обычный `RELAY` ко всем сообщениям, кроме `EXTEND2`. Сторожевой узел, считающий ранние ячейки, потенциально способен отличить этот упрощённый клиент от обычного Tor. Различие оставлено ради ясности, а на полной схеме сеанса в книге показано поведение основной реализации.

Выходной узел отвечает сообщением `CONNECTED` с допустимым форматом тела (IPv4, IPv6 или пустым) либо `END` с кодом причины. `EXITPOLICY` указывает на отказ выходного узла по его политике, а `CONNECTREFUSED` — на отказ целевой стороны установить соединение. Непосредственный опыт с политикой выхода описан в [лабораторной работе 14](Лабораторная-14-Политика-выхода.md).

Протокол разрешает отправлять прикладные данные ещё до `CONNECTED`, экономя одну круговую задержку цепи (RTT). Учебный клиент для наглядности сначала ожидает `CONNECTED`.

## Управление потоком и важная ошибка

```python
def count_received_data(self) -> None:
    """Вызывать для каждой DATA-ячейки от финального hop: отправлять SENDME
    с аутентификацией (version 1) каждые `sendme_inc` ячеек."""
    est = dict(self.exit_extensions)
    sendme_inc = est[2][0] if 2 in est else 100
    self.data_to_ack += 1
    if self.data_to_ack == sendme_inc:
        self.data_to_ack = 0
        # Digest — running digest после распознанной ячейки, вызвавшей
        # SENDME: sendme_digest в src/core/crypto/relay_crypto_tor1.c.
        digest = self.crypto.hops[-1].backward.digest.digest()
        body = struct.pack(">BH", 1, 20) + digest
        self.send(RelayMessage(RelayCommand.SENDME, 0, body))
        self.sendme_sent += 1
```

**Этот метод относится к `Circuit`, а не к `Stream`.** Изначально у каждого потока был собственный счётчик, поэтому моменты отправки хешей подтверждения расходились с состоянием цепи, когда предыдущий поток уже израсходовал часть окна.

Остальные элементы также важны:

- **`sendme_inc`** берётся из расширения 2, согласованного с выходным узлом во время рукопожатия ([лабораторная работа 3](Лабораторная-03-Handshake.md)). В данном примере оно равно 31 при управлении перегрузкой и 100 в историческом режиме. Это согласованный параметр, а не неизменяемая константа клиента.
- **Хеш** — накопительный хеш обратного направления последнего узла *после* обработки ячейки `DATA`, вызвавшей `SENDME`. Это внутреннее состояние, известное стороне, обработавшей соответствующий трафик.
- **Версия 1 и длина 20 байт** обозначают аутентифицированный формат `SENDME` уровня цепи на основе SHA-1. Версия 0 не содержала хеш и позволяла подделывать подтверждения; предложение 289 добавило аутентификацию.
- **StreamID 0** указывает на сообщение управления всей цепью. В историческом режиме у отдельных потоков собственные окна и подтверждения; при согласованном управлении перегрузкой они не используются.

> Аутентифицированное `SENDME` — не цифровая подпись. Оно служит **подтверждением получения**: знание нужного накопительного хеша указывает на обработку соответствующих ячеек.

## Цикл приёма

```python
def receive_all(self) -> bytes:
    """Читать DATA до END, при необходимости отправляя circuit SENDME."""
    parts = []
    while not self.closed:
        _, msg = self._next()
        if msg.command == RelayCommand.DATA:
            parts.append(msg.data)
            self.reg.received_data += len(msg.data)
            self.reg.data_cells += 1
            self.circ.count_received_data()
        elif msg.command == RelayCommand.END:
            self.closed = True
            self.reg.others.append(f"END {END_REASONS.get(msg.data[0] if msg.data else 1)}")
        else:
            self.reg.others.append(RelayCommand(msg.command).name)
    return b"".join(parts)
```

Подсчёт ячеек и отправка подтверждений происходят **внутри цикла приёма**. Если клиент перестаёт читать данные, он не отправляет новые подтверждения, а отправитель со временем исчерпывает своё окно. Так управление потоком непосредственно связано с приёмом.

`self.reg` собирает статистику: количество байтов, ячеек `DATA` и остальных сообщений. Это помогает объяснить, почему передача часто требует больше ячеек, чем теоретический минимум `ceil(bytes / 498)`: выходной узел отправляет данные по мере получения, не ожидая полного заполнения каждой ячейки.

## Измерение окна

```python
circ = build(path, cc=cc)
circ.count_received_data = lambda: None      # не отправлять SENDME уровня цепи
```

Подмена метода пустой функцией допустима только в частной лаборатории. Она позволяет узнать, **сколько ячеек отправит выходной узел до остановки из-за исчерпания окна**.

В историческом примере наблюдались 124 ячейки при управлении перегрузкой и 500 без него. Результат зависит от конфигурации и от того, какое окно исчерпается раньше: при отсутствии управления перегрузкой ограничение потока в 500 ячеек срабатывает прежде номинального окна цепи в 1000.

## Что важно знать для успешного запуска

- Нужен **сервер на порту 8080**. Его использует и `make verify-labs`, поэтому перед полной проверкой ручной сервер нужно остановить.
- Тестовый файл должен быть достаточно большим для исчерпания окна. При объёме менее примерно 124 ячеек (около 60 КБ) эффект управления перегрузкой трудно заметить.
- Идентификаторы StreamID должны быть **уникальными для активных потоков одной цепи и ненулевыми**.
- Если большая передача завершается `DESTROY`, проверьте общий учёт `SENDME` уровня цепи, а также журналы и возможные другие причины ошибки.
