## Что демонстрирует лаборатория

Tor не направляет весь прикладной трафик по одному и тому же каналу (circuit). Он учитывает **учётные данные SOCKS**, с которыми обращается приложение. Tor Browser применяет этот механизм для разделения контекстов разных сайтов: при включённом `IsolateSOCKSAuth` (обычно по умолчанию) потоки с различными учётными данными **не могут совместно использовать одну цепочку**. Это **не означает**, что для каждой вкладки выбирается отдельная цепочка или что IP-адреса выходных узлов обязательно различаются.

Если работает Conflux, один логический **туннель Conflux** может состоять из двух связанных цепочек. Чтобы правильно оценить изоляцию, нужно сопоставлять туннели, а не только одну из ветвей.

## Подготовка

```bash
# При первом запуске: make -C labs/ru/лаборатория image
make -C labs/ru/лаборатория start
# Локальный HTTP-сервер, принимающий тестовые запросы на порту 8080
python3 -m http.server 8080 --bind 127.0.0.1 &
```

Скрипт запускается **внутри контейнера** и обращается к ControlPort клиента через Stem. Каталог `labs/ru/лаборатория` монтируется как `/lab`; пути `/labs/ru/лаборатория/isolation.py` **внутри контейнера нет**. Используется сетевая конфигурация Docker `--network host`, поэтому локальный сервер доступен контейнеру. Параметр `curl --noproxy ""` в скрипте запрещает переменной окружения `NO_PROXY` обходить SOCKS-прокси:

```bash
docker exec -w /lab torbook-network python3 /lab/isolation.py
```

Не запускайте одновременно лабораторные сети разных языковых изданий: они используют общие порты.

## Исторический пример вывода (не гарантируется)

```text
учётные данные site-a.example  -> conflux 90EFE5BD       ['test004r', 'test005r', 'test007e']
учётные данные site-a.example  -> conflux 90EFE5BD       ['test004r', 'test005r', 'test007e']
учётные данные site-b.example  -> conflux A608C1C1       ['test004r', 'test006e', 'test007e']
учётные данные -               -> conflux 2FED7F85       ['test004r', 'test003r', 'test007e']
(NEWNYM задержан на 6 с)
после NEWNYM, site-a.example -> conflux BA715C26
```

Как читать результат:

- Первые два запроса используют **одинаковые** учётные данные и в этой конкретной пробе попадают в один туннель. Повторное использование **разрешено, но не гарантируется**: Tor вправе выбрать другую совместимую цепочку.
- Разные учётные данные при включённом `IsolateSOCKSAuth` не должны совместно использовать цепочку; отличающиеся идентификаторы здесь это иллюстрируют, но не доказывают различие выходных IP-адресов.
- После `NEWNYM` **новые запросы** должны использовать чистые цепочки. Сам сигнал **не равнозначен** функции Tor Browser «Новая личность»: браузер также закрывает вкладки и окна, очищает cookie и другие данные.
- Запись `conflux XXXXXXXX` показывает только первые восемь символов `CONFLUX_ID`; список узлов относится к одной из двух ветвей. Если Conflux не используется, скрипт может показать `circuit N`.

## Три проблемы, обнаруженные в ходе эксперимента

1. **Tor создаёт собственные потоки.** Запросы к каталогам и другие служебные операции могут порождать события `STREAM`. Поэтому скрипт отбирает события по целевому адресу и использует последнее подходящее событие `SUCCEEDED`.
2. **`NEWNYM` может ограничиваться по частоте.** В версии Tor из исходного опыта интервал `MAX_SIGNEWNYM_RATE` составлял 10 секунд. Спецификация допускает ограничение частоты без обязательного фиксированного интервала для всех версий. Ранний сигнал в наблюдавшемся случае **откладывался** и мог повлиять на следующий запрос. Скрипт читает предупреждение и ждёт указанное время, однако отсутствие предупреждения само по себе не гарантирует завершения обработки сигнала.
3. **Conflux соединяет две цепочки в один туннель.** Если сравнивать только отдельные ветви по `CONFLUX_LINKED`, корректная изоляция может ошибочно показаться нарушенной.

В небольшой частной сети доступно мало вариантов маршрута, поэтому результаты могут отличаться. Итальянская автоматизированная проверка повторяет опыт до трёх раз; это не делает повторное использование одной цепочки обязательным свойством Tor.

## Автоматическая проверка

Проверка `lab11` находится в **итальянском** файле `scripts/verify_labs.py` и анализирует повторное использование туннеля, различие учётных данных и эффект `NEWNYM`. Первый критерий характеризует исторический опыт и **не является протокольной гарантией**.

Русскоязычный `isolation.py` **только выводит наблюдения** и сам по себе не проверяет указанные условия и не завершает выполнение с ошибкой при их нарушении. Команда `make -C labs/ru/лаборатория verify` проверяет состояние сети посредством Chutney, но не выполняет итальянскую проверку `lab11`.

## Известные проблемы

| Симптом | Возможная причина |
|---|---|
| Скрипт не находит потоки | HTTP-сервер на порту 8080 не запущен или целевой адрес в скрипте не совпадает с ним. |
| Одинаковые учётные данные попали в разные туннели | Tor может выбрать иную подходящую цепочку; одно только различие туннелей не означает нарушение изоляции. |
| `SocketError` при подключении к ControlPort | Скрипт запущен на хосте вместо контейнера либо клиентская служба не готова. |
