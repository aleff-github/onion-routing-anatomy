## Что демонстрирует эта работа

В собственной частной сети сравниваем TLS-трафик к обычному ORPort с соединением obfs4. В исторической записи TLS начинался с `16 03 01`, а на порту obfs4 анализатор не обнаружил заголовков TLS. **Это результат конкретной записи, а не гарантия полной неразличимости.** Наблюдатель всё ещё видит адреса, время, объёмы трафика и может заблокировать известный IP-адрес моста.

При обычном TLS-зондировании рукопожатие obfs4 не было завершено. Спецификация требует отвергать неверное рукопожатие и **рекомендует** случайную задержку перед разрывом TCP; она не обещает бесконечного молчания.

## Подготовка

**Защита данных лаборатории:** `make ... clean` удаляет `лаборатория/net/`, включая закрытые ключи и журналы. Используйте только одноразовую сеть и сохраните важные файлы отдельно. Если образ ещё не построен, сначала выполните `make -C labs/ru/лаборатория image`: команда `start` не создаёт образ. Сети разных языков используют общие порты и не должны быть запущены одновременно.

Используется отдельная топология с bridge authority `003ba`, obfs4 bridge `009br` и bridge client `011bc`.

```bash
make -C labs/ru/лаборатория clean
make -C labs/ru/лаборатория start NETWORK=book-bridge
```

Чтобы затем вернуться к обычной сети:

```bash
make -C labs/ru/лаборатория clean
make -C labs/ru/лаборатория start
```

Когда `book-bridge` запущена, `make -C labs/ru/лаборатория verify` выполняет end-to-end checks Chutney именно для этой активной topology.

В этой топологии bridge client использует **SocksPort 9011**, а transport obfs4 bridge слушает **9909**.

## Шаг 1 — Клиент подключается через bridge

```bash
grep -E "new bridge descriptor|Only one bridge|Bootstrapped 100" labs/ru/лаборатория/net/nodes/011bc/notice.log
```

```text
[notice] new bridge descriptor 'test009br' (fresh): $DE539956E7E6A323...~test009br at 127.0.0.1
[warn] Only one bridge (transport: 'obfs4') is configured. You should have at least two
       for conflux, for any transport that is not 'snowflake'.
[notice] Bootstrapped 100% (done): Done
```

Журнал показывает, что клиент получил дескриптор заранее настроенного моста и завершил загрузку. **Само сообщение не доказывает, по какому каналу был получен дескриптор.** Адрес моста и параметры транспорта obfs4 должны быть предоставлены заранее: мост не указан в обычном публичном консенсусе. Предупреждение Conflux относится к одному мосту в этой конфигурации, а не к ошибке загрузки.

```bash
docker exec torbook-network curl -s -o /dev/null -w "%{http_code}\n" \
  --noproxy "" --socks5-hostname 127.0.0.1:9011 http://127.0.0.1:8080/
```

```text
200
```

Для этой проверки на порту 8080 должен работать локальный HTTP server.

## Шаг 2 — Что видит цензор

Предварительно запустите в другом терминале локальный HTTP-сервер: `python3 -m http.server 8080 --bind 127.0.0.1`. Следующий опыт **перезаписывает** `b1.pcap`: сначала сохраните нужную запись. Захватите оба вида трафика, а затем дождитесь завершения tcpdump.

Внутри контейнера захватите одновременно трафик к obfs4 port bridge и к обычному ORPort, затем создайте оба вида соединения:

```bash
# Только собственная одноразовая сеть Chutney
docker exec -u 0 -d torbook-network sh -c \
  "timeout 25 tcpdump -i lo -w /lab/net/b1.pcap 'tcp port 9909 or tcp port 5104' >/dev/null 2>&1"
sleep 2
docker exec torbook-network curl --silent --show-error --max-time 15 \
  --noproxy "" --socks5-hostname 127.0.0.1:9011 http://127.0.0.1:8080/
# Откройте также обычный Tor-канал к локальному узлу
PYTHONPATH=labs/ru/код python3 - <<'PY'
import ssl
from torlab.channel import ChannelError, open_channel
from torlab.laboratory import relay
r = relay("004r", client="010c")
open_channel("127.0.0.1", r.port, expected_identity=r.id_ed)
PY
sleep 27  # дождитесь окончания tcpdump
for p in 5104 9909; do
  echo "== порт $p =="
  docker exec torbook-network tshark -r /lab/net/b1.pcap \
    -Y "tcp.dstport==$p && tcp.len>0" -T fields -e tcp.len -e tcp.payload | head -1
  docker exec torbook-network tshark -r /lab/net/b1.pcap \
    -Y "tls && tcp.port==$p" -T fields -e frame.number | wc -l
done
```

Величины далее относятся к **исторической записи**, а не к новому запуску. Префикс `16 03 01` содержит старое поле версии TLS и **не подтверждает согласованную версию**. Фильтр Wireshark `tls` — инструмент наблюдения, а не доказательство невозможности классификации обфусцированного потока. obfs4 не скрывает известный IP-адрес моста.

```text
== порт 5104, первые байты от клиента ==
1533   16030105f8010005f4030305cc9ad005e921614509b15f6151135f983b...
== порт 9909, первые байты от клиента ==
602    f23abb4e8c3a45ab0e92958157c177bba1cc5dd27e80d74db45d77b425...

== пакеты, распознанные как TLS ==
порт 5104: 29
порт 9909: 0

== размеры сегментов obfs4 (клиент -> bridge) ==
602 1762 1308 1414 643 2183 2195 1568 1308 2037 616 1346
```

Как читать capture:

- **`16 03 01`** — начало TLS handshake record. Трафик обычного ORPort распознаётся как TLS, поэтому цензор видит protocol-level structure и адрес, который может уже быть известен как публичный Tor relay.
- Трафик obfs4 не начинается сопоставимой TLS-структурой. В записанном capture **ноль** пакетов были классифицированы как TLS, а segment sizes не соответствовали напрямую 514-байтовым Tor cells.
- Точные bytes, packet counts и segment sizes меняются между run. Важно различие между узнаваемым TLS и obfuscated transport.

## Шаг 3 — Проверка моста обычным TLS-клиентом

Если подозревается bridge, цензор может попытаться подключиться к порту и говорить на известном протоколе. В нашей приватной лаборатории обычный Tor-channel code из [лабораторной работы 1](Лабораторная-01-Канал.md), направленный на obfs4 port, даёт:

```bash
PYTHONPATH=labs/ru/код python3 - <<'PY'
import ssl
from torlab.channel import ChannelError, open_channel
from torlab.laboratorio import relay
r = relay("004r", client="010c")
try:
    open_channel("127.0.0.1", 9909, expected_identity=r.id_ed)
    raise AssertionError("неожиданно удалось установить обычный TLS-канал через obfs4")
except (TimeoutError, ssl.SSLError, ConnectionResetError, ChannelError) as exc:
    print(type(exc).__name__ + ":", exc)
PY
```

```text
TimeoutError: _ssl.c:1063: The handshake operation timed out
```

Обычный TLS ClientHello не является корректным рукопожатием obfs4. В историческом опыте полезного ответа до тайм-аута не было, но возможны также позднее закрытие или сброс соединения. Число `_ssl.c:1063` зависит от версии Python/OpenSSL. **Один зонд не доказывает полной невидимости моста**. Для подлинного подключения нужны выданные заранее параметры транспорта и сертификат моста.

## Автоматическая проверка

`make -C labs/ru/лаборатория verify` проверяет **активную топологию Chutney**, но не выполняет шесть специальных проверок итальянского `make verifica-lab-bridge`, не создаёт автоматически обе трассы и не проводит TLS-зондирование.

```bash
make -C labs/ru/лаборатория verify
```

Команда `verify` сама не переключает topology. Сначала явно запустите `book-bridge`, проверьте её, затем очистите и снова запустите обычную `book`.

## Известные проблемы

Команда `make -C labs/ru/лаборатория clean` предназначена только для одноразового окружения. `pkill -x tor` остановит **все** процессы Tor внутри данного контейнера, а не только мост.

| Симптом | Причина |
|---|---|
| Bootstrap bridge-сети не завершается | Процессы `tor` предыдущей topology могли удержать порты. В одноразовой лаборатории их можно остановить через `docker exec torbook-network pkill -x tor`. |
| `011bc` не запускается | Client nodes относятся ко второй startup phase; неполный ручной запуск может их пропустить. |
| `tshark` не находит пакетов | Capture мог начаться после трафика. Сначала запустите `tcpdump`, немного подождите, затем создайте соединения. |
| Номера узлов отличаются | Chutney нумерует их по `labs/ru/лаборатория/chutney/networks/book-bridge`; проверьте `labs/ru/лаборатория/net/nodes/`. |
