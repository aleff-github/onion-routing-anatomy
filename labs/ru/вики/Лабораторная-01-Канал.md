## Что демонстрирует эта работа

TLS-сертификат реле **не является доказательством его идентичности**. Он самоподписанный, и такой сертификат может создать кто угодно. Реле подтверждает идентичность *внутри* канала через ячейку `CERTS`: Ed25519-идентичность связывается с ключом подписи, а ключ подписи — с отпечатком используемого TLS-сертификата. Только проверка всей цепочки и сравнение полученной идентичности с реле, к которому мы намеревались подключиться, предотвращают подмену выбранного узла посредником.

## Запуск эксперимента

```bash
python3 - <<'EOF'
from torlab.channel import open_channel, identity_from_file

expected = identity_from_file("labs/ru/лаборатория/net/nodes/003r/fingerprint-ed25519")
c = open_channel("127.0.0.1", 5103, expected_identity=expected)
print(c.version, c.ed_identity.hex()[:16] + "...", c.netinfo, c.auth_methods)
for r in c.registry:
    print("  ", r)

# отрицательная проверка: relay правильного типа, но с другой identity
try:
    open_channel("127.0.0.1", 5104, expected_identity=expected)
except Exception as e:
    print("port 5104 with 003r identity ->", e)
EOF
```

## Ожидаемый вывод

```text
5 785d3199f21d20ad... Netinfo(timestamp=1790265613, peer_address='127.0.0.1', my_addresses=['127.0.0.1']) [3]
   TLS TLSv1.3 TLS_AES_256_GCM_SHA384
   <- VERSIONS (6 байт)
   <- CERTS (1456 байт)
   <- AUTH_CHALLENGE (36 байт)
   <- NETINFO (509 байт)
   -> NETINFO: канал открыт

port 5104 with 003r identity -> идентичность реле отличается от ожидаемой
```

Как читать результат:

- **`5`** — согласованная версия link protocol. Клиент предлагает версии 4 и 5, как Arti; версия 3 здесь уже не нужна.
- Шестнадцатеричная идентичность реле **будет отличаться от примера**: свежая инициализация лабораторной сети создаёт новые ключи. По той же причине длина ячейки `CERTS` может немного отличаться.
- **`[3]`** — методы аутентификации, которые реле готово принять от *другого реле*. Мы действуем как клиент и не аутентифицируем себя. Если бы клиент это делал, он получил бы стабильную узнаваемую identity между каналами, что противоречит нашей цели.
- В `NETINFO` relay сообщает своё время и адрес, с которого видит клиента. Наш ответ намеренно содержит **нулевую временную метку и ни одного адреса**: клиент не должен раскрывать собственные часы и адреса.
- **В историческом примере** только что открытый канал не получил ячеек `PADDING`. Их появление зависит от использования цепи, согласованных настроек и параметров сети: одношаговый канал не требует обязательного padding. Многошаговый пример [лабораторной работы 4](Лабораторная-04-Шифрование.md) может его показать, но отдельные запуски различаются.

## Ключевая отрицательная проверка

Последняя строка — самая важная часть эксперимента. Мы соединяемся с relay `004r`, одновременно заявляя, что ожидаем идентичность `003r`, и код корректно отклоняет соединение. Параметр `expected_identity` нельзя опускать в этом опыте: API допускает `None`, и в таком случае сравнение с заранее выбранным узлом не выполняется.

Реализация, проверяющая signatures и сроки действия сертификатов, но **не сравнивающая итоговую identity с ожидаемой**, может пройти все положительные тесты и при этом не защищать от подмены реле.

Каждый некорректный вариант должен быть отклонён.

# Подробности реализации

`labs/ru/код/torlab/channel.py` содержит примерно 260 строк. Модуль открывает TLS-соединение, проверяет идентичность удалённого узла и возвращает объект `Channel`, через который следующие лабораторные работы отправляют ячейки.

Приведённые ниже фрагменты взяты из `labs/ru/код/torlab/channel.py`: импорты и константы определены в полном модуле, и отдельные фрагменты не являются самостоятельными программами.

## Почему одного TLS недостаточно

```python
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
```

Для специалиста по безопасности эти строки могут выглядеть как серьёзная ошибка. В данном контексте это не так.

TLS-сертификат реле Tor **самоподписанный** и не содержит проверяемого доменного имени. Обычные центры сертификации не аутентифицируют реле, поэтому стандартная CA-проверка Python просто отклонила бы каждое такое соединение. Идентичность проверяется **внутри** канала через `CERTS`; эта цепочка сертификатов привязана к реальной TLS-сессии fingerprint текущего сертификата.

Иными словами: TLS обеспечивает шифрование; Tor обеспечивает аутентификацию реле.

> Копирование этих трёх строк в обычный HTTPS-клиент **отключило бы его сертификатную защиту**. Здесь они допустимы только потому, что код немедленно проверяет полную цепочку Tor-сертификатов и сопоставляет её с заранее выбранной идентичностью реле.

```python
if os.environ.get("SSLKEYLOGFILE"):
    ctx.keylog_filename = os.environ["SSLKEYLOGFILE"]
```

Это стандартное соглашение, которым пользуются и браузеры: если задан `SSLKEYLOGFILE`, TLS-библиотека экспортирует секреты сессии, чтобы Wireshark мог расшифровать захват. Именно это используется в [лабораторной работе 12](Лабораторная-12-Трафик.md). Мы расшифровываем **собственный** трафик собственными добровольно экспортированными ключами.

```python
source = (source_address, 0) if source_address else None
```

Аргумент `source_address` выбирает локальный адрес источника, например `127.0.0.2`. Он используется в [лабораторной работе 9](Лабораторная-09-DoS.md), где разные исходящие адреса позволяют проводить контролируемые проверки защиты от DoS.

## Цепочка сертификатов

```python
def verify_responder_identity(certificates: dict[int, bytes], cert_tls_der: bytes) -> bytes:
    """Применить правила раздела "Authenticating the responder from its CERTS".

    Вернуть KP_relayid_ed (32 байта), если цепочка
        Ed25519 identity -> signing key -> TLS certificate
    действительна; иначе вызвать ChannelError.
    """
    try:
        id_v_sign = decode_ed_certificate(certificates[CERT_IDENTITY_V_SIGNING])
        sign_v_tls = decode_ed_certificate(certificates[CERT_SIGNING_V_TLS_CERT])
    except KeyError as e:
        raise ChannelError(f"отсутствует сертификат типа {e.args[0]}") from None

    identity = id_v_sign.signing_key
    if identity is None:
        raise ChannelError("IDENTITY_V_SIGNING без signing key")
    id_v_sign.verify_signature(identity)                      # самоподписан identity key
    signing_key = id_v_sign.certified_key             # KP_relaysign_ed
    sign_v_tls.verify_signature(signing_key)
    if sign_v_tls.certified_key != hashlib.sha256(cert_tls_der).digest():
        raise ChannelError("TLS: SIGNING_V_TLS_CERT не соответствует полученному TLS-сертификату")
    for c in (id_v_sign, sign_v_tls):
        if c.expired():
            raise ChannelError(f"сертификат типа {c.kind} просрочен")
    return identity
```

Эта функция последовательно выполняет несколько разных проверок аутентификации:

| Компонент | Что делает | Что предотвращает |
|---|---|---|
| Type 4 | Связывает идентичностью реле с его signing key | Произвольный signing key, выдающий себя за relay |
| `signing_key` | Читает **кто подписал** из extension 4 | Вывод identity по контексту вместо извлечения из сертификата |
| Self-signature | Проверяет внутреннюю согласованность type-4 certificate | Сама по себе даёт мало: self-signed certificate может создать любой |
| Type 5 | Связывает signing key с TLS-сертификатом | Цепочку, не относящуюся к текущей сессии |
| SHA-256 fingerprint | Привязывает всё к **этому соединению** | Посредника, предъявляющего сертификаты честного relay в своей TLS-сессии |
| Срок действия | Отклоняет устаревшие сертификаты | Использование выведенных из эксплуатации signing keys |

Самая важная проверка — сравнение fingerprint TLS-сертификата. Без неё цепочка могла бы быть подлинной, но бесполезной: она доказывала бы лишь существование relay с такой identity, а не то, что текущее соединение установлено именно с ним.

**Identity здесь не является обычным полем сертификата:** это ключ, подписавший сертификат и переданный в extension 4. Сертификат фактически говорит: «Я, X, сертифицирую ключ Y». X нужно читать из extension, а не выводить из источника сертификата.

## Проверка, которой нет внутри этой функции

```python
identity = verify_responder_identity(certificates, cert_tls)
if expected_identity is not None and identity != expected_identity:
    raise ChannelError("идентичность реле отличается от ожидаемой")
```

Корректная certificate chain доказывает, что мы разговариваем **с каким-то** relay; она ещё не доказывает, что это **выбранный нами relay**. Сравнение с `expected_identity` превращает общую аутентификацию в аутентификацию конкретного peer. Именно эту проверку мы намеренно заставляем сработать при подключении к 5104 с fingerprint `003r`.

Реализация, проверяющая signatures и expiration, но забывающая это сравнение, проходит положительные тесты и всё равно остаётся уязвимой к подмене.

## Цикл handshake

```python
while netinfo is None:
    cell, buffer = _read(sock, buffer, version)
    registry.append(f"<- {CellCommand(cell.command).name} ({len(cell.body)} байт)")
    if cell.command == CellCommand.VERSIONS:
        if version:
            continue                                  # последующие ячейки VERSIONS игнорируются
        version = negotiate_version(SUPPORTED_VERSIONS, cell.body)
    elif cell.command == CellCommand.VPADDING:
        continue
    elif cell.command == CellCommand.CERTS:
        certificates = decode_certs(cell.body)
    elif cell.command == CellCommand.AUTH_CHALLENGE:
        (n,) = struct.unpack(">H", cell.body[32:34])
        methods = [m for (m,) in struct.iter_unpack(">H", cell.body[34:34 + 2 * n])]
    elif cell.command == CellCommand.NETINFO:
        netinfo = decode_netinfo(cell.body)
    else:
        raise ChannelError(f"неожиданная ячейка во время handshake: {cell.command}")
```

- **Цикл завершается при получении `NETINFO`**, а не после жёстко заданного количества ячеек. Handshake заканчивается сообщением протокола; промежуточные ячейки могут отличаться.
- Повторная `VERSIONS` **игнорируется**, как требует спецификация. Без `continue` версия могла бы неожиданно измениться посреди handshake.
- `AUTH_CHALLENGE` разбирается только для фиксации предложенных методов. Клиент не аутентифицируется, чтобы не получать стабильную узнаваемую identity.
- Последняя ветвь принципиальна: **всё, что явно не разрешено, считается ошибкой**. `VPADDING` можно безопасно отбрасывать, потому что спецификация разрешает её в любой момент. Другие неожиданные ячейки handshake отклоняются.

Сразу после цикла находится легко забываемая проверка:

```python
if certificates is None:
    raise ChannelError("NETINFO получена до CERTS")
```

Без неё вредоносный peer мог бы немедленно отправить `NETINFO` и обойти аутентификацию: цикл завершился бы до получения `CERTS`.

## Наш NETINFO

```python
channel.send(client_netinfo_cell(host))
```

Наш ответ `NETINFO` содержит **нулевую временную метку и не сообщает собственный адрес**. Это не лабораторное упрощение: настоящий Tor client ведёт себя так же. Собственное время могло бы раскрывать относительно стабильный clock skew, а адреса — сведения, которые клиенту незачем публиковать.

## Что важно знать для успешного запуска

- **Fingerprints меняются при каждой полной переинициализации сети.** `identity_from_file` читает `labs/ru/лаборатория/net/nodes/<node>/fingerprint-ed25519`. Содержимое имеет вид `<name> <base64-key>` без конечного `=`; код восстанавливает padding перед decoding.
- **Порт всегда равен `5100 + номер узла`.**
- Канал сам не генерирует padding и не поддерживает соединение активным. Неиспользуемый канал может быть закрыт relay через несколько минут.
- Только что открытый канал не получает `PADDING`. Relay включает padding после того, как канал использовался для **полной** цепи, проходящей дальше этого relay, либо для пользовательского трафика. В `channelpadding.c` это состояния `CHANNEL_USED_FOR_FULL_CIRCS` и `CHANNEL_USED_FOR_USER_TRAFFIC`. Наши one-hop-цепи не подходят; padding становится виден в [лабораторной работе 4](Лабораторная-04-Шифрование.md). После достижения порога он может начаться **до** первого данных приложения; это регулируется параметром консенсуса `nf_pad_before_usage`, по умолчанию равным 1.
