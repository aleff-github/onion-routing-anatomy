## What This Demonstrates

A cryptographic handshake can be implemented directly from the specification and made to interoperate with an independent implementation—which is the only convincing validation. It also shows how a relay reacts when validation fails: flipping one bit in the MAC produces a `DESTROY` with reason `PROTOCOL`, not a convenient error message.

This laboratory covers four handshakes at once: plain ntor-v3, ntor-v3 negotiating congestion control, classic ntor, and `CREATE_FAST`.

## Run the Experiment

```bash
python3 - <<'EOF'
from torlab.channel import open_channel
from torlab.cells import Cell, CellCommand, describe
from torlab.laboratory import relay
from torlab.ntor import *

g = relay("003r")
c = open_channel("127.0.0.1", g.port, expected_identity=g.id_ed)

def create(circ, htype, hdata):
    c.send(Cell(circ, CellCommand.CREATE2, create2_body(htype, hdata)))
    r = c.receive()
    print("<-", describe(r, c.version))
    return r

# 1. ntor-v3, without extensions
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([]))
r = create(0x80000001, HTYPE_NTOR_V3, hd)
sm, _ = ntor3_client_finish(st, hdata_created2(r.body))
print("   ntor-v3 ok, relay message:", decode_extensions(sm))

# 2. ntor-v3 requesting congestion control
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([(1, b"")]))
r = create(0x80000002, HTYPE_NTOR_V3, hd)
sm, _ = ntor3_client_finish(st, hdata_created2(r.body))
print("   ntor-v3 with CC_FIELD_REQUEST ok, response:", decode_extensions(sm))

# 3. classic ntor
st, hd = ntor_client_start(g.id_rsa, g.ntor)
ntor_client_finish(st, hdata_created2(create(0x80000003, HTYPE_NTOR, hd).body))
print("   ntor ok")

# 4. CREATE_FAST (only for one-hop circuits: it relies on TLS)
x, body = create_fast_client()
c.send(Cell(0x80000004, CellCommand.CREATE_FAST, body))
r = c.receive(); print("<-", describe(r, c.version))
complete_create_fast(x, r.body); print("   CREATE_FAST ok")

# 5. deliberately flip one MAC bit
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([]))
r = create(0x80000005, HTYPE_NTOR_V3, hd[:-1] + bytes([hd[-1] ^ 1]))
assert r.command == CellCommand.DESTROY and r.body[0] == 1
print("   reason:", r.body[0], "(modified MAC)")

# 6. CGO requested without congestion control
st, hd = ntor3_client_start(g.id_ed, g.ntor, encode_extensions([(3, b"\x02\x06")]))
r = create(0x80000006, HTYPE_NTOR_V3, hd)
assert r.command == CellCommand.DESTROY and r.body[0] == 1
print("   reason:", r.body[0], "(CGO requested without congestion control)")
EOF
```

## Expected Output

```
<- CircID=0x80000001 CREATED2 body=509 bytes
   ntor-v3 ok, relay message: []
<- CircID=0x80000002 CREATED2 body=509 bytes
   ntor-v3 with CC_FIELD_REQUEST ok, response: [(2, b'\x1f')]
<- CircID=0x80000003 CREATED2 body=509 bytes
   ntor ok
<- CircID=0x80000004 CREATED_FAST body=509 bytes
   CREATE_FAST ok
<- CircID=0x80000005 DESTROY body=509 bytes
   reason: 1 (modified MAC)
<- CircID=0x80000006 DESTROY body=509 bytes
   reason: 1 (CGO requested without congestion control)
```

How to interpret it:

- The relay's CC_FIELD_RESPONSE extension (type 2) reports `sendme_inc = 0x1f = 31`, the **SENDME acknowledgement interval in DATA cells** negotiated for congestion control. Proposal 324 chose 31 partly because it is close to the number of fixed cells fitting in a maximum TLS record; this is **not** a TLS record-size rule. The same congestion-control parameter appears again in [Laboratory 5](Laboratory-05-Streams.md) and in the onion descriptor discussed in [Laboratory 8](Laboratory-08-Onion-services.md).
- **Reason 1 means `PROTOCOL`.** Here the relay can expose the actual local reason because the error occurred at this relay. When relaying a `DESTROY` generated by another node, it must not expose information that would reveal where along the circuit the problem happened.
- The final case demonstrates a dependency between extensions: CGO requires congestion control. Requesting CGO alone is not a valid configuration.
- In this recorded private-network example no `PADDING` cells appeared. Padding behavior depends on negotiation, circuit activity and parameters; the absence here does not establish a protocol-wide rule.

## Why Test Vectors Matter

A cryptographic handshake is not validated merely because two implementations can talk to each other. Two implementations making the same mistake could interoperate perfectly. `test_ntor.py` reproduces the **official test vectors**: Proposal 332 for ntor-v3 and Proposal 216 for ntor's HKDF. Inputs, including supposedly random keys, are fixed, and outputs must match byte for byte. Additional tests ensure that a modified `AUTH` or a different `VER` string causes the handshake to fail.

`hmac.compare_digest` avoids a straightforward first-difference early exit when comparing authentication values of the same type and length; it is not a guarantee that an entire application has constant-time behavior.

## Known Problems

| Symptom | Cause |
|---|---|
| `LookupError: no microdescriptor for 003r` | The client has not downloaded microdescriptors yet. Wait about a minute after network startup or check bootstrap. |
| `CREATE2` elicits `DESTROY` (command 4) | A circuit-creation error, which may reflect an invalid handshake, unsupported extension, stale keys or transient relay state. Inspect the reason code and private-network logs before retrying; it is not always a temporary load condition. |
| `HandshakeError: invalid ntor-v3 AUTH` | You are using keys from another relay or from a previous network initialization. |

# Implementation, in Detail

`labs/en/code/torlab/ntor.py` is about 240 lines. It should be written with the specification open beside it and validated against test vectors. In cryptography, “works” does not mean “correct.”

The inline function listings are excerpts from the per-language `ntor.py` and `test_ntor.py`; imports, types and constants are defined in those complete files. The reference transcript is historical and can vary with relay state and negotiated parameters.

## The Primitives

```python
NTOR3_PROTOID = b"ntor3-curve25519-sha3_256-1"

def _t(name: str) -> bytes:
    return NTOR3_PROTOID + b":" + name.encode()

def _encap(s: bytes) -> bytes:
    return struct.pack(">Q", len(s)) + s

def _h3(s: bytes, t: bytes) -> bytes:
    return hashlib.sha3_256(_encap(t) + s).digest()

def _mac3(k: bytes, msg: bytes, t: bytes) -> bytes:
    return hashlib.sha3_256(_encap(t) + _encap(k) + msg).digest()

def _kdf3(s: bytes, t: bytes, length: int) -> bytes:
    return hashlib.shake_256(_encap(t) + s).digest(length)
```

These lines directly implement the formulas in Appendix A.1 of Proposal 332. They illustrate three general design ideas.

**Domain separation.** `PROTOID` participates in every calculation. This prevents a value produced in this protocol from being mistaken for a value from a different protocol using the same primitive and possibly the same keys.

**Tweaks.** One hash construction is separated into purpose-specific functions: `kdf_phase1`, `msg_mac`, `key_seed`, `verify`, `kdf_final`, and `auth_final`. Without explicit domain separation between these purposes, values derived for one role could be confused with another.

**Encoding structure.** `_encap` prefixes each byte string with its 8-byte length, making concatenation **unambiguous**. Without lengths, pairs such as (`"ab"`, `"c"`) and (`"a"`, `"bc"`) would both become `"abc"`. Correct cryptographic encoding must include structure, not only contents.

One detail matters: in `_mac3`, the *key* is encapsulated while the message is not. That is the proposal's exact definition. Making the function “more regular” by encapsulating both would break interoperability, and the test vectors would immediately reveal the change.

## Phase 1: The Client Message

```python
def ntor3_client_start(ID: bytes, B: bytes, message: bytes, ver: bytes = CIRCUIT_VERIFICATION,
                        x: bytes | None = None) -> tuple[Ntor3State, bytes]:
    """CREATE2 HDATA for ntor-v3: ID (32) | B (32) | X (32) | encrypted MSG | MAC (32)."""
    sk, X = x25519_generate(x)
    Bx = x25519_dh(sk, B)
    fase1 = _kdf3(Bx + ID + X + B + NTOR3_PROTOID + _encap(ver), _t("kdf_phase1"), 64)
    enc_k1, mac_k1 = fase1[:32], fase1[32:]
    msg_cifrato = aes_ctr(enc_k1, message)          # AES-256-CTR
    mac = _mac3(mac_k1, ID + B + X + msg_cifrato, _t("msg_mac"))
    return Ntor3State(sk, X, B, ID, Bx, mac, ver), ID + B + X + msg_cifrato + mac
```

The client creates an ephemeral pair (`sk`, `X`) and computes **`Bx`**, a Diffie–Hellman value combining its ephemeral private key with the relay's **static** `ntor-onion-key`. From that value it derives two keys, one for encrypting its handshake message and one for authenticating it.

> **This first phase by itself does not provide forward secrecy for the encrypted client message.** `Bx` depends on the relay's static key; future compromise of that key could expose recorded phase-1 messages. The protocol therefore places negotiated options in `CM`, not long-lived application secrets. Circuit key material gains forward secrecy in phase 2.

The optional `x` argument exists only for testing. It lets the test harness fix an otherwise random secret key and reproduce the proposal's vectors exactly.

The default `ver` string is `b"circuit extend"` for circuit extension. It is encoded into the derivation, so changing even one byte changes derived keys. This prevents a handshake transcript created for one purpose from being reused in a different protocol context.

## Phase 2: The Relay Response

```python
def ntor3_client_finish(st: Ntor3State, response: bytes,
                      length=CIRCUIT_KEY_MATERIAL_LEN) -> tuple[bytes, bytes]:
    """Response = Y (32) | AUTH (32) | MSG. Return (relay message, key stream)."""
    Y, auth, msg = response[:32], response[32:64], response[64:]
    secret_input = (x25519_dh(st.x, Y) + st.Bx + st.ID + st.B + st.X + Y
                    + NTOR3_PROTOID + _encap(st.ver))
    key_seed = _h3(secret_input, _t("key_seed"))
    verify = _h3(secret_input, _t("verify"))
    auth_input = (verify + st.ID + st.B + Y + st.X + st.mac + _encap(msg)
                  + NTOR3_PROTOID + b"Server")
    if not hmac.compare_digest(_h3(auth_input, _t("auth_final")), auth):
        raise HandshakeError("invalid ntor-v3 AUTH")
    stream = _kdf3(key_seed, _t("kdf_final"), 32 + length)
    return aes_ctr(stream[:32], msg), stream[32:]
```

`secret_input` combines **two** Diffie–Hellman values, each with a distinct role:

| Value | What it combines | Purpose |
|---|---|---|
| `Yx` (`x25519_dh(st.x, Y)`) | Client ephemeral × relay ephemeral | **Forward secrecy**: long-term keys alone cannot reconstruct it |
| `Bx` | Client ephemeral × relay static | **Authentication**: only the relay holding the matching static private key can derive it |

This is the core of ntor: one handshake provides both properties. Removing `Bx` would remove relay authentication; removing `Yx` would remove forward secrecy.

Using `hmac.compare_digest` is not cosmetic. It avoids an obvious early-exit comparison on the first mismatching byte and is the correct primitive for verifying authentication values.

The final key stream is longer than the circuit keys alone. The first 32 bytes decrypt the relay's handshake message; the following 72 bytes become `Df`, `Db`, `Kf`, and `Kb`, which [Laboratory 4](Laboratory-04-Encryption.md) uses for relay-cell protection.

## Test Vectors, and Why They Are the Real Validation

Vectors provide strong, repeatable evidence of conformity to the published examples, but do not on their own establish the security or correctness of every execution path.

```python
def test_ntor3_vectors_proposal_332():
    st, hdata = ntor3_client_start(h(V["ID"]), h(V["B"]), h(V["CM"]), ver=h(V["VER"]), x=h(V["x"]))
    assert hdata.hex() == V["client"]
    sm, key_stream = ntor3_client_finish(st, h(V["server"]), length=256)
    assert sm == h(V["SM"])
    assert key_stream[:32].hex() == V["keystream_start"]
```

A cryptographic handshake should be checked against fixed inputs and fixed byte-for-byte outputs. `test_ntor.py` reproduces Proposal 332's complete ntor-v3 vector and Proposal 216's vectors for ntor HKDF. Other tests deliberately modify `AUTH` and `ver` and require failure; a verifier that accepted everything would otherwise pass the positive vector.

## The Four Variants and When to Use Them

| Handshake | When | Notes |
|---|---|---|
| **ntor-v3** | Current default where supported | Can negotiate options in an encrypted message |
| **ntor** | Relays without the newer relay protocol capability | No negotiation message, only key establishment |
| **CREATE_FAST** | Only for **one-hop** circuits | No DH; relies on the underlying TLS channel |
| TAP | Never in current tor | Removed in tor 0.4.9.1-alpha |

`CREATE_FAST` is appropriate only when the first hop is also the last—for example, certain directory circuits—because it adds no independent Diffie–Hellman exchange beyond TLS. It should not be substituted for ntor when building ordinary multi-hop circuits.

## What You Need to Know to Make It Work

- **Relay keys** (Ed25519 identity and `ntor-onion-key`) are loaded by `torlab.laboratory.relay("003r")` from network files and client microdescriptors. If the client has not downloaded them, wait briefly after network startup.
- **Use a fresh CircID for each trial.** Reusing an already open CircID results in `DESTROY`.
- The high bit of the CircID must be set for a circuit created by the channel initiator (`0x80000001`, not `0x00000001`), preventing CircID collisions between the two endpoints.
- Completing the handshake does not by itself create a data stream. After `CREATED2`, you have a one-hop circuit and key material; [Laboratory 4](Laboratory-04-Encryption.md) adds relay-cell encryption and extension.
